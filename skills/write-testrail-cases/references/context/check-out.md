## What is Check out

The Check out app allows library staff to lend items to patrons by scanning (or manually entering) patron cards and item barcodes. Staff select a service point, find the patron using a barcode, username, external system ID, or custom field, then scan item barcodes to create loans. The app applies circulation rules, enforces loan policies, patron blocks, and item limits, and handles proxy borrowing, multipiece items, check out notes, due date overrides, and patron-facing note pop-ups.

> **Identifier convention for this area:** write circulation cases with **symbolic placeholders the executor fills at run time** — `service point S`, `<patron barcode>`, `<item barcode>`, `<title>` — not invented concrete values. Do NOT fabricate a specific barcode or a named service point; concrete values only when the exact value is itself under test.

## Key Terms

| Term | Definition |
|---|---|
| Patron | Library user borrowing an item |
| Proxy | A patron acting on behalf of another patron (sponsor); the item is checked out to the sponsor |
| Sponsor | The patron on whose behalf a proxy acts |
| Circulation rule | A rule mapping combinations of patron group, material type, loan type, and effective location to a loan policy |
| Loan policy | Defines loan period, renewability, and closed-library due date management |
| Patron block | A manual or automated block preventing checkout; can be overridden with a comment |
| Item block | A block triggered by item limits in loan/material type rules; can be overridden |
| Check out note | A note attached to an item record that must be acknowledged before checkout proceeds |
| Multipiece item | An item where "Number of pieces" > 1; requires confirmation modal before checkout |
| Service point | Physical or virtual desk where checkout occurs; must be assigned to the staff user |
| DCB loan | Digital Cloud Borrowing loan; hides patron/staff info buttons in the action menu |
| Use at location | Hold shelf designation for items that patrons must use on-site |

## Lifecycle / Workflow

```
Staff opens Check out app
        │
        ▼
Scan patron card (barcode / username / external system ID / custom field / patron look-up)
        │
        ├─→ [Patron not found] → "User with this {identifier} does not exist" error
        ├─→ [Patron has no barcode] → "User does not have a barcode" error modal on item scan
        ├─→ [Patron has blocks] → "Patron blocked from borrowing" modal → Override or Close
        ├─→ [Patron has notes] → "Note for patron" modal → Close or Delete note (one at a time)
        └─→ [Proxy relationship] → "Who are you acting as?" modal → Self or Proxy for <sponsor>
                │
                ▼
        Scan item barcode
                │
                ├─→ [Item has check out note] → "Confirm check out" modal → Confirm or Cancel
                ├─→ [Multipiece item] → "Confirm multipiece check out" modal → Check out or Cancel
                ├─→ [Item status: Withdrawn/Missing/Lost and paid] → "Check out {status} item?" modal → Confirm or Close
                ├─→ [Item status: Checked out] → "Item not checked out" modal: "Item is already checked out"
                ├─→ [Item status: Declared lost / Claimed returned] → "Item not checked out" modal with status-specific message
                ├─→ [Non-loanable, no override permission] → Modal: item not loanable, Close only
                ├─→ [Non-loanable, with override permission] → Modal: item not loanable, Override + Close
                │       └─→ "Override loan policy" modal → date/time selector + required comment → Save & close
                └─→ [Success] → Item added to Scan items list with loan policy, due date, time
                        │
                        ▼
                End session (or scan next patron)
```

| Item Status | Checkout behaviour |
|---|---|
| Available | Checked out directly (or with modals) |
| Checked out | Blocked — "Item is already checked out" |
| Declared lost | Blocked — status-specific message |
| Claimed returned | Blocked — status-specific message |
| Withdrawn | Requires confirmation modal |
| Missing | Requires confirmation modal |
| Lost and paid | Requires confirmation modal |

## Proxy Borrowing

A **proxy** is a patron who checks out items on behalf of another patron (the **sponsor**).

### Requirements
- The proxy relationship must be set up in the **Users app** on the sponsor's user record first.
- Cannot proxy for someone not configured in Users.

### Proxy checkout flow
1. Scan proxy patron's barcode.
2. **"Who are you acting as?"** dialog appears:
   - `{proxy} is acting as: Self` (radio button checked)
   - `Or acting as proxy for: {sponsor}` (radio button)
3. Select sponsor → click **Continue**.
4. Borrower section shows sponsor's details; Borrower's proxy section shows proxy's details.
5. Loan is recorded against the **sponsor's** account; proxy is noted.

### Inactive Proxy/Sponsor (Trillium)
- When proxy's expiration date is in the past: red warning displays in "Who are you acting as?" modal; the "acting as proxy for" radio is NOT clickable. C1263905 writes the text as **"Proxy user record expired"**, but the only matching ui-checkout key is `proxyExpired` = **"Proxy relationship expired"** (en.json) — the case text is DRAFT and not in the translations.
- When sponsor's expiration date is in the past: red warning **"Sponsor user record expired"** (`sponsorExpired`, en.json) displays; radio button for sponsor is NOT clickable.
- The "Who are you acting as?" modal is shared (stripes-smart-components); the expiry warnings were reported incorrect in UICHKOUT-976 (modal named the sponsor as inactive when the proxy was the expired user; Jira status Closed) and the clickable-radio part is tracked in STSMACOM-948/949.
- ⚠️ C1263905 is still DRAFT (updated 2026-04-24; steps marked "DRAFT ... Will be implemented in STSMACOM-949") — verify in env, do not model new cases on it.
- API: `proxyUserBarcode` is a separate optional field of `POST /circulation/check-out-by-barcode` (see API surface).

  2. `Confirm multipiece check out` → click Check out

## Check out Notes

- Notes assigned to an item in Inventory (Loan and availability accordion).
- At checkout, the `Confirm check out` modal appears; notes sorted most-recently-added first.
- Each note shows: date/time added, note text, user who added it (Lastname, Firstname).
- Clicking **Confirm** proceeds with checkout; clicking **Cancel** does not check out.
- After checkout, notes accessible via item action menu → `Check out notes`.

## Patron Notes Popup at Check Out [confirmed — C356781]

Distinct mechanic from the item-level "Check out Notes" above — this is for notes assigned to the **user record**, not an item.

- Source: `Users app > <user record> > Notes accordion > New` — a note has a **`Check out app`** checkbox (alongside a `Users app` checkbox) controlling where it surfaces; only notes with `Check out app` checked pop up here.
- Trigger: scanning/entering the patron's barcode + Enter in the **Scan patron card** pane (i.e. on patron lookup itself, before any item is scanned).
- Display: a **`Note for patron`** modal appears, one at a time, showing the single most-recently-created qualifying note. Buttons: `Close`, `Delete note`.
- Multiple qualifying notes are shown **sequentially**, one modal per note — clicking `Delete note` deletes that note and closes its modal, then immediately opens the next note's `Note for patron` modal (does not require re-scanning the patron). `Close` dismisses the current modal without deleting and **also opens the next note's modal** (C380512 step 9: first modal closes, second `Note for patron` modal shows `Close` + `Delete note`); after the last `Close` the `Scan patron card` (with user info) and `Scan items` panes are shown.
- After `Close` on all notes, scanning item barcodes in the same session does NOT re-show the note modals (C380512 steps 11-12); the notes are not deleted — in the Users app the note still exists with the `Check out app` selection unchanged (C380512 last step).
- After all qualifying notes are dismissed via `Delete note`, the patron's `Scan patron card` + `Scan items` panes are shown normally, and re-opening the user's own record shows the `Notes` accordion as `No notes found`.
- A user whose capabilities include no note-delete action (C380718/C380719 preconditions: only `Data - UI-Notes Item - Create` (capability set name not confirmed — verify), `Procedural - UI-Notes Item Assign-Unassign - Execute` (Cypress create-role-only-sets.cy.js), `Data - UI-Users - View` (Cypress capabilitySets.js)) sees only the `Close` button in the pop-up (C380718 expected result); `Delete note` appears for users with `Data - UI-Notes Item - Delete` (capability set name not confirmed — verify) (C380512 preconditions). The permission link is unverified (inferred from the cases only; no translation/permission source).
- Two patrons in a row (C356847, C380513, C380718, C380719): the second patron's note pop-up is shown whether or not `End session` was used between the patrons, and also when the first patron had no notes. Build separate cases for "with End session" and "without End session" — each is a separate TestRail case.
- Note creation: `Notes` accordion > `New` > fields `Note type`, `Note title`, `Details`, checkboxes `Check out app` / `Users app` (C380512; smart-components keys `notes.displayAsPopup.checkout` = `Check out app`, `notes.displayAsPopup.users` = `Users app`, `notes.displayAsPopup.label` = `Display note as a pop-up`).
- UIU-3485 (see delta below) added suppression of the pop-up for the session; no TestRail case or translation found for it — verify in env.

## For Use at Location (reading room) at Check out

> Sources: UICHKOUT-962, UICHKOUT-965, UICHKOUT-966 (DRAFT, not implemented), Confluence 1779171329 and 694812699, ui-checkout CHANGELOG 13.0.0, `ScanItems.js`, en.json.

- Feature is off unless the backend env var `ENABLE_FOR_USE_AT_LOCATION` is true (Confluence 1779171329). Loans with a loan policy that has `For use at location` enabled are "for use at location" loans; at check out the item gets circ action `In use` (Confluence).
- Daily cycle: item checked in to the hold shelf with Check in action `Keep on hold shelf` (loan stays open, item status stays Checked out, circ log action `Held`) and checked out again next day via Check out (ui-checkout then calls `pickup-by-barcode-for-use-at-location`, not `check-out-by-barcode`).
- Before 13.0.0 the app answered `Item is already checked out` for such items (UICHKOUT-965 description); the fix is a BREAKING change (new `loan-storage` interface).
- After scanning the patron, the awaiting-pickup modal (`awaitingPickupLabel` = `Items awaiting pickup`) shows `awaitingPickupMessage` (requested items awaiting pickup at this service point) and, as a second line, `awaitingPickupMessageHeld` (items held for use at location at this service point); if the patron has only regular loans, the second line does not show (UICHKOUT-962). If the patron has both, there are two lines (Confluence 1779171329).
- The "use at location" columns for the Scan items list (UICHKOUT-966) are DRAFT only — do not assert such columns.
- No TestRail case in section 116 covers this; related TestRail section is `Circulation > For use at location (reading room circulation)` (id 72019, not read here).

## Common Verification Patterns

> Copy these into expected results. They reflect how the team actually writes assertions for this area.

### Pattern 1: Successful checkout — item appears in Scan items list

```
Action:   Scan patron barcode → scan item barcode → no blocking modals.
Expected: Item row appears in Scan items pane: No. | Barcode | Title | Loan policy | Due date | Time | Action
          "Open loans" counter on Scan patron card pane is incremented by 1.
          "Total items scanned: N" label at bottom of Scan items pane is updated.
```

### Pattern 2: Due date cut-off by patron expiration

```
Action:   Loan period extends past patron expiration date.
Expected: "Due date" in Scan items list = patron's expiration date.
          "Time" = 11:59 PM.
          Flag icon displayed next to due date with tooltip "System calculated due date adjustment".
```

**Interaction with Closed Library Due Date Management (confirmed, C343265):** when the patron's expiration date itself falls on a day the check-out service point is **closed**, the truncated due date is further shifted by the loan policy's `Closed library due date management` setting — same as any other due date: `Keep the current due date` leaves it on the (closed) expiration day, `Move to the end of the previous open day` / `Move to the end of the next open day` shifts it accordingly. A due-date-truncation case should therefore test the 2×2 matrix (expiration falls on an open day / a closed day) × (each `Closed library due date management` option), not just the simple "loan period exceeds expiration" case — the flag/tooltip appears in every variant.

### Pattern 3: Override non-circulating item

```
Action:   Scan patron + item → item-not-loanable modal → click Override →
          fill required Comment field + set date/time → Save & close.
Expected: Modal closes. Item is checked out to patron.
          Due date = date/time set in Override modal.
          In Loan action table (Loan details page):
            Action = "Checked out through override"
            Action date = checkout date/time
            Due date = overridden date/time
            Source = "Lastname, Firstname Middlename" (linked to user profile)
            Comments = text entered in override modal
```

### Pattern 4: Multiple modals — ordering

```
Item has check out note AND is multipiece AND triggers non-loanable policy.
Order of modals:
  1. "Confirm check out" (check out note) → click Confirm
  2. "Confirm multipiece check out" → click Check out
  3. "Item not checked out" (non-loanable) → click Override or Close
```

### Pattern 5: Patron note pop-up sequence

```
Action:   Scan patron card for patron with 2 notes assigned to "Check out app".
Expected: "Note for patron" modal appears with most recently added note.
          Modal shows: note title, note text, date/time added, user who added it (Lastname, Firstname).
          Buttons: "Close" and "Delete note".
          After clicking Close: first modal closes; second modal appears with next note.
          After all notes dismissed: checkout proceeds normally.
```

### Pattern 6: Patron block override

```
Action:   Scan patron with manual block → "Patron blocked from borrowing" modal
          → click Override → enter comment → Save & close.
Expected: Patron block overridden. Comment saved on loan record.
          If patron has > 3 blocks: only 3 shown + "View block details to see additional reasons for block..."
```

### Pattern 7: Circulation rule verification via Loan details

```
Action:   Check out item matching specific material type circulation rule.
Expected: "Loan details" page shows correct Loan policy, Overdue fine policy, Lost item fee policy
          matching the applicable circulation rule (not fallback).
Action:   Check out item with no matching rule.
Expected: Loan policy matches the fallback rule.
```

## Authoring style (measured 2026-07-23)

Check-out is small (~34 cases), **mixed Type (~51% `Functional` / 43% `Other`)**, median ~6 steps, `User Journey` ~6% (used for a few multi-branch cases like `Cancel check out multipiece items` C934249). Cases are scenario-focused and fairly compact: the loan-policy / patron-block / proxy / custom-field / service-point setup lives in Preconditions (symbolic identifiers `S`, `<barcode>`, `<patron>` per circulation convention — do NOT invent concrete barcodes), and steps scan patron + item and assert the one behavior under test (block modal, override, multipiece confirm, note popup, due date). Lean `Functional` for real check-out behavior, `Other` for pure UI/display checks (zoom/overlap, empty fields, pagination). Several DRAFT/NOT-IMPLEMENTED cases exist (proxy expiry, non-requester override) — don't model new cases on those.

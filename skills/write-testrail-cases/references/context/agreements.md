## What is Agreements

The Agreements app is part of FOLIO's Electronic Resource Management (ERM) suite. It manages contracts with content vendors for electronic resources — defining what content the library can access, under what terms, for what period. An agreement record is the central hub connecting vendors (Organizations), licensing terms (Licenses app), acquisitions spend (Orders app POLs), e-resource content (internal Local KB or external eHoldings), usage statistics (eUsage), and notes. The app is built on `mod-agreements` (Grails/Groovy) and `ui-agreements` (React/Stripes). Released UI version: **12.1.x (Trillium R1 2026)**; master is **12.2.0 (Umbrellaleaf, in progress)** — adds resourceName sort/404 handling (ERM-4019, ERM-4103), new supplementary-property name validation (ERM-4101) and a "Connected tasks/jobs" fourth pane on Agreement and Agreement line views (ERM-4156; `src/components/ConnectedTasksJobs/` renders the `task-list` plugin, so it only appears when a task-list plugin module is installed). Backend `mod-agreements` 7.4.0 (2026-10-20) added on-demand GOKb package pull (ERM-4161) and the eHoldings v5.0 API (ERM-4140).

## Key Terms

| Term | Definition |
|---|---|
| **Agreement** | A contract record describing content access rights with a vendor |
| **Agreement line** | A single e-resource entry (package or title) covered by the agreement |
| **E-resource** | An electronic resource — can be a Package, a Title (PCI), or Unlinked |
| **Internal KB** | FOLIO's own local knowledge base (managed via Local KB admin app) |
| **External KB / eHoldings** | Third-party KB (e.g. EBSCO) accessed via eHoldings integration |
| **GOKb** | Global Open Knowledgebase — external title/package registry for search integration (added Trillium) |
| **Package** | A collection of e-resource titles from a provider |
| **PCI** | Package Content Item — individual title within a package |
| **Basket** | Temporary holding area for selected e-resources before adding to an agreement |
| **Platform** | Delivery platform for e-resources; can have proxy and URL customization settings |
| **POL** | Purchase Order Line from the Orders app, linked to an agreement line |
| **Acquisition Unit** | Controls record-level access to agreements (view/edit/create/delete) |
| **Supplementary property** | Custom metadata field (text, integer, decimal, date, pick list) defined in Settings |
| **Supplementary document** | File attachment or URL associated with an agreement record |
| **Controlling license** | The primary license governing this agreement (only one allowed per agreement) |

## Record Hierarchy / Architecture

```
Agreement
├── Agreement periods (1+ required)
├── Agreement lines (0+)
│   ├── Linked to Internal KB package or title
│   ├── Linked to eHoldings resource (package or title)
│   ├── Unlinked (manual / description only)
│   ├── Linked PO lines (0+)
│   ├── Custom coverage (if e-resource linked)
│   └── Documents (0+)
├── License information
│   ├── Controlling license (0 or 1)
│   ├── Historical licenses (0+)
│   ├── Future licenses (0+)
│   └── Supplemental licenses (0+)
├── Organizations (0+, each with a role)
├── Internal contacts (0+, linked to Users app)
├── Supplementary properties (0+)
├── Supplementary documents (0+)
├── Related agreements (0+, each with a relationship type)
├── Usage data providers (0+, linked to eUsage)
├── Tags (0+)
├── Notes (0+)
└── Acquisition units (inherited / assigned)
```

## Lifecycle / Workflow

| Status | Description | Additional fields |
|---|---|---|
| **Active** | Agreement is currently in force | — |
| **Draft** | Being prepared, not yet in effect | — |
| **In negotiation** | Under discussion with vendor (default label is lower-case "n" — mod-agreements `SubscriptionAgreement.groovy` `@Defaults`) | — |
| **Requested** | Requested but not yet active | — |
| **Closed** | Terminated or expired | **Reason for closure** (optional; in the create/edit form the field is always present but **disabled** unless Status = Closed — ui-agreements `src/components/AgreementSections/FormInfo/FormInfo.js`) |

> Note: defaults come from mod-agreements `SubscriptionAgreement.groovy` (`@Defaults(['Draft', 'Requested', 'In negotiation', 'Active', 'Closed'])`). Agreement status is an **internal** pick list (`@CategoryId(defaultInternal=true)`): per docs.folio.org Settings_agreements "Pick list values", internal default pick lists can only have their **labels** edited — `New` is greyed out and no trash-can icon is shown, so values cannot be added or deleted. Labels may differ per tenant.
> No status-transition restrictions exist: any status can be set from any other; the only coupled rule is that the backend nulls `reasonForClosure` whenever status ≠ `closed` (`SubscriptionAgreement.checkAgreementStatus()`), and the UI warns first (`warn.clearReasonForClosure`).

### Reason for Closure values (configurable defaults)
`Cancelled`, `Ceased`, `Superseded`, `Rejected` (mod-agreements `SubscriptionAgreement.groovy` `@Defaults`; the earlier `Completed` value has no source — removed 2026-11-24)

### Renewal priority values (configurable defaults)
`Definitely renew`, `For review`, `Definitely cancel` (mod-agreements `SubscriptionAgreement.groovy` `@Defaults`)

## Status Values

### Agreement Status / Renewal priority / Reason for Closure
See **Lifecycle / Workflow** above (same values, sources and rules; Status is an internal pick list — labels editable only; Reason for closure is disabled unless Status = Closed and is not required).

### Related agreement relationship types (hard-coded in UI)
`supersedes` / `is superseded by`, `provides post-cancellation access for` / `has post-cancellation access in`, `tracks demand-driven acquisitions for` / `has demand-driven acquisitions in`, plus `has_backfile_in` and `related_to` types (ui-agreements `src/constants/agreementRelationshipTypes.js` — a constant list, **not** a Settings pick list).

### Agreement Line Type
`External` (eHoldings/GOKb), `Internal` (Local KB), `Unlinked`

### Package Synchronisation Status
`Enabled` / `Disabled` (en.json `eresources.syncContentsFromSource.true/false`, `eresources.syncStatus.true/false`); filter option `Not set` (`eresources.syncStatus.notSet`). In the package **view** an unset value shows `-` (ERM-3670). Backend values of `syncContentsFromSource` transitions are `PAUSED` ↔ `SYNCHRONIZING` (en.json `eresources.syncPackageSuccess.PAUSED/SYNCHRONIZING`; ERM-4161).

### Is Perpetual / Content review needed
`Yes`, `No` (internal `Global.Yes_No` pick list — mod-agreements `SubscriptionAgreement.groovy`)

### License link status (this agreement)
`Current`, `Future`, `Historical`, `Supplemental`

### Supplementary Property Types (Settings > Agreements > Supplementary properties)
`Text`, `Integer`, `Decimal`, `Date`, `Pick list` (single), `Pick list (multi-select)`. Same field set as Licenses terms: Label, Name, Description, Category (optional), Order weight, Deprecated, Default visibility, Primary property. (cases — C358544)

### Supplementary Property "Name" field validation (confirmed, C1385635)
- Same underlying character rule as Licenses terms — must start with a letter, then only letters/digits/underscores — **but the UI error message differs from Licenses**: for a non-blank invalid value (leading digit/underscore, embedded space, hyphen, `@`, `.`, etc.) Agreements shows the **specific** message `The name must start with a letter, and can only contain letters, numbers, and underscores.` (Licenses instead shows the generic `Please fill this in to continue` for the same class of invalid input.) Don't copy Licenses' expected-result wording into an Agreements supplementary-property test or vice versa — verify which app you're documenting.
- A truly **blank** Name field still shows the generic `Please fill this in to continue` in both apps.
- Unicode letters are valid as the leading character too (e.g. `ΔeltaProperty`), matching the Licenses term-name rule.
- The (i) tooltip text (en.json `supplementaryProperty.help.name`, corrected 2026-11-24) starts `A supplementary property 'name' is used when outputting the supplementary property data in a machine readable format intended to be used by external systems or programs that access the agreement supplementary property data.` — full text in the Changes section below. The older `An agreement term 'name'...` wording (and the `An supplementary property` quirk recorded from C1385635) survives only in the lagging en_US.json; assert the en.json text and verify in env.

## Performance / Pagination Notes

- **Agreement Lines accordion badge count uses a lightweight `perPage=1` request, not a full fetch** — when editing (or viewing) an agreement with >200 agreement lines, the Network tab shows exactly ONE request to `/entitlements` with `perPage=1`; the accordion header shows the correct total count from that single request's metadata rather than paging through all records just to display a number. Only expanding the accordion (or clicking through to the full agreement-lines search) triggers the paginated fetch of actual line data. (cases — C413361)
- **Agreement Lines accordion loads 5 at a time via "Load More"** — first expand shows exactly 5 agreement lines with a `Load More` button below; each click appends the next batch and re-displays `Load More` until all lines are loaded, at which point the button disappears. Same "Load More" pattern applies to the sibling accordions on E-resource records (`E-resources in package`, `Options for acquiring e-resource`, `Agreements for this e-resource` — each independently configurable via "Adjust number... shown at a time", per C196794–C196797). (cases — C350626)
- **Linked Agreements / related-entitlements lists over 200 records batch at 100 per request** — same pattern as documented for Licenses' linked-agreements accordion (see licenses.md); applies analogously to Agreements' >200-line and >200-related-entitlement scenarios (C389581/C413361, C389584, C389586). ## Usage Data Provider Linking (confirmed C345311)

Before an agreement line can show Cost-per-Use figures (see below), a **usage data provider** record must be explicitly linked to the agreement — this is a separate, prerequisite step, not automatic:

1. Open the Agreement, click Edit, and expand the `Usage data` accordion (independently hideable via `Settings > Agreements > Display settings > Hide accordions in agreement edit view`, like any other optional accordion).
2. Click `Add usage data provider` — a new card appears with a `Link usage data provider` option.
3. Click `Link usage data provider` to open a usage-data-provider search/sort modal; selecting a provider closes the modal and populates the card with that provider's details.
4. An optional free-text `Note` field is available on the card.
5. `Save & Close` persists the link; requires the `eUsage: Can view usage data providers and usage reports` permission to even see the accordion.

## eUsage Cost-Per-Use Calculation (confirmed formula, C1307930 and sibling cases in section 94077)

For an agreement line with a linked usage-data-provider and one or more linked invoice lines covering the same subscription period:

```
Cost per request (total)  = (sum of linked invoice-line amounts − linked credit-note amounts) / Total item requests
Cost per request (unique) = (sum of linked invoice-line amounts − linked credit-note amounts) / Unique item requests
```

Example from C1307930: two invoices (250 + 350 = 600) minus one credit note (150) = 450; 450 / 76 total item requests = 5.92 (total); 450 / 52 unique item requests = 8.65 (unique). This nets multiple invoices/credit notes for the **same** subscription period into a single combined cost figure — don't treat each invoice as producing its own separate cost-per-use row. The downloaded CSV (via "Download CSV" on the Cost per use view) includes: paid amount, total item requests, unique item requests, cost per request (total), cost per request (unique), and usage broken down by year of publication (`0001` = COUNTER report did not specify a publication year).

## Local KB Admin — Import Error Handling (confirmed, C343295)

- An invalid KBART import (e.g. missing mandatory columns) still completes as a **job** rather than failing the upload outright: job's "Import outcome" = `Failure`, Error log shows the specific missing-fields message `The import file is missing the mandatory fields: [{field1}, {field2}]`, and the Info log shows `Job execution failed`. ## External eHoldings Resource-Name Sync (resourceName backfill)

> Extends Rule 14 (eHoldings resourceName auto-populates on line creation) with the backfill/edge-case behavior — confirmed C1347207, C1348606.

- If the resourceName on an external (eHoldings) agreement line is null (e.g. via direct API edit, or historically before this feature existed) AND the underlying eHoldings resource still exists, it gets backfilled by either: (a) the scheduled `ExternalEntitlementEholdingsSyncJob` (interval set via environment variable) or (b) a manual trigger — authorized user sends `GET /erm/admin/triggerEntitlementEholdings` (add `?force=true` if the job already ran today).
- **If the underlying eHoldings resource has been deleted/removed by the time of sync**, the agreement line permanently shows only the bare `EKB-{type}: {reference}` (no resource name in parentheses) and is **not a hyperlink**; opening that line's detail view shows an `Error 404: Not Found` error card in the Agreement line information section. This is a stable, expected end state — don't treat it as a bug in a test case, and don't expect the name to ever populate for a line whose resource no longer exists.
- Job results appear in **Local KB Admin** app (filter Job type = "External eHoldings entitlements"): `Import outcome` = `Success` (0 errors) or `Partial success` (partial errors, e.g. one resource not found via eHoldings bulk fetch); Info log entries follow the format `ResourceName for {type} entitlement {agreementLineUUID} with EKB ID: {reference} updated to {resourceName}`; the log's `Export` button downloads a JSON file (`EHoldingsEntitlementSyncJob__{timestamp}_info`) with a toast `Creating log export file... this may take a few minutes for large logs.`
- If a subsequent sync run finds zero agreement lines with a null resourceName, **no job log entry is generated at all** — this is expected, not a failure to trigger.

## Acquisition Units / Access Control (Sunflower+ — ERM-3718 family)

- Acq units are assigned on the **agreement** (create/edit form, type-down sorted A–Z case-insensitive — ERM-3850) and **inherited by its agreement lines** (ERM-3777, ERM-3780).
- View pane: `Acquisition units` accordion on Agreement and Agreement line; **closed by default** and **hidden when no unit is assigned** (ERM-3779, ERM-3780 QA comments).
- Restricted user (not a member of a unit restricting Edit/Delete): `Edit`, `Delete` and the Agreement lines accordion `New agreement line` action are shown **greyed out and inactive**, not hidden (ERM-3781, ERM-3782, ERM-3906 — also check keyboard navigation cannot open the form).
- Backend enforces the same: `POST /erm/entitlements` for a protected agreement is rejected (ERM-3862); adding from the basket to a non-editable agreement shows `basket.update.error.callout` (ERM-3866); `/clone` is rejected when the user cannot view the agreement (ERM-3959).
- A unit that restricts **Create (claim)** blocks both adding **and removing** that unit unless the user is a member (ERM-3812). Only **changed** policies are evaluated on claim, so an agreement already carrying a claim-restricted unit can still be edited by a non-member (ERM-3809).
- Saving shows two toasts: `Agreement updated: {name}` and, only if units changed, `Agreement acquisition units updated: {name}` (ERM-3808, ERM-3820).
- Filters: `Acquisition units` filter on Agreements search (ERM-3783) and Agreement lines search (ERM-3784), list sorted A–Z case-insensitive (ERM-3849).
- Acq units can be switched off per deployment by environment variable; then no acq-unit UI and no calls to mod-orders (ERM-3807).

## Key Business Rules for Test Cases

1. **Name and Status are the only required agreement fields** — plus at least one period with a Start date. (ui-agreements `src/components/AgreementSections/FormInfo/FormInfo.js` `requiredValidator` on Name and `agreementStatus`; mod-agreements `SubscriptionAgreement.groovy` `name(nullable:false, blank:false, unique:true)`, `agreementStatus(nullable:false)`; `Period.groovy` `startDate(nullable:false)`; C757)
1a. **`Record created` / `Record last updated` metadata** — on creation both are equal; after an edit `Record last updated` advances while `Record created` stays fixed (shared ERM pattern; commonly asserted in create/edit cases like C757). (C757)
1b. **Empty accordions are hidden in the view pane** — a freshly created agreement shows only `Agreement lines`, `Supplementary properties`, `Notes`; accordions like `All periods`, `Internal contacts`, `External licenses`, `Organizations`, `Supplementary documents`, `Usage data`, `Related agreements`, `Controlling license`, `Future licenses`, `Historical licenses`, `License and business terms` appear only once they have content. (cases — C163926)
2. **At least one period required** — agreement cannot be saved without an agreement period. (cases + mod-agreements `SubscriptionAgreement.groovy` `periods(minSize: 1)`)

## Authoring style (measured 2026-07-23)

Agreements is **`Other`-heavy (~89%)** with only ~9% `Functional`, median ~8 steps, `User Journey` ~9%. Most cases are record-CRUD and accordion-management on the Agreement record (add/edit/remove agreement lines, periods, related agreements, supplementary properties/documents, organizations, internal contacts, tags, notes) plus Settings for pick lists / supplementary-property types — the team labels these `Other`. Reserve `Functional` for computed behavior (eUsage Cost-Per-Use calculation, resourceName sync). Preconditions carry the ERM setup (an existing Agreement with the relevant accordion populated, a linked eHoldings resource or POL, a configured supplementary-property/pick list). Multi-accordion or cost-per-use cases run a bit longer; single-accordion edits stay compact.

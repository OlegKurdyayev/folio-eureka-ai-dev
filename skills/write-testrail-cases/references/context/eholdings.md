## What is eHoldings

The eHoldings app manages the library's electronic resource holdings via an external knowledge base (KB). It connects to EBSCO's HoldingsIQ API — currently the **only supported external KB**. Changes made in FOLIO eHoldings or EBSCO Holdings Management are **immediately reflected** in both interfaces (real-time sync via API).

eHoldings allows libraries to:
- Browse and search providers, packages, and titles from the EBSCO KB
- Select/deselect packages and titles for the library's holdings
- Edit coverage settings, proxy settings, and custom labels
- Create custom packages and titles
- Link e-resources to Agreements in the Agreements app
- View usage & analysis (cost-per-use) data exported via Export Manager

---

## Key Terms

| Term | Definition |
|---|---|
| Provider | Content vendor (e.g. Elsevier, Wiley) — sourced from EBSCO KB; not editable |
| Package | Collection of titles from a provider; can be KB or custom |
| Title | Individual e-resource (journal, e-book, etc.) |
| Resource | A title in the context of a specific package (title + package combination) |
| KB | Knowledge base — EBSCO HoldingsIQ; the only supported external KB |
| Custom package | Library-created package (not from KB); can be deleted |
| Custom title | Library-created title linked to a custom package; can be deleted |
| Holdings status | Whether the library has selected (added) a package or title |
| Access status type | Library-defined label for a title's local access status |
| Usage Consolidation | SUSHI-based cost-per-use analytics feature requiring separate configuration |

---

## Record Hierarchy / Architecture

```
Provider (content vendor, e.g. Elsevier, Springer)
  └── Package (collection of titles, e.g. "Elsevier Freedom Collection")
        └── Title (individual e-resource, e.g. a journal or e-book)
              └── Resource (title in context of a specific package = title + package combination)
```

All Provider, Package, and Title KB data lives in EBSCO's knowledge base — FOLIO accesses it via HoldingsIQ API. Only library-local data (selection state, coverage, proxy overrides, custom labels, tags, notes) is stored in FOLIO.

## Lifecycle / Workflow

### Package / Title Holdings Status

| Status | Description |
|---|---|
| **Not Selected** | Exists in KB but not in library's holdings (default for KB content) |
| **Selected** | Library has added this package/title to their holdings |
| **{ N } of { M } titles selected** | Package is partially selected (some titles added) |

Status transitions require `Procedural - UI-Eholdings Package-Title Select-Unselect - Execute`.

### Package Visibility — "Hide/exclude all titles in the package" (UIEH-1500, MODKBEKBJ-840)

The old "Show titles in package to patrons" label (Show to patrons / Not shown to patrons) is **replaced** — do not assert it. The package record now has a `Hide/exclude all titles in the package` group with one checkbox per category:

| Category (edit) | View label | Search filter label |
|---|---|---|
| `In Publication Finder` | `Publication Finder` | `Hidden in Publication Finder` |
| `In Full Text Finder` | `Full Text Finder` | `Hidden in Full Text Finder Resolver` |
| `In MARC export` | `MARC export` | `Excluded from MARC export` |

- View summary: `Package is set to hide/exclude in {category1}` / `… in {category1} and {category2}` / `… in {category1}, {category2}, and {category3}`; list rows show `Package is hidden`.
- Hiding requires a reason / reason code on the backend (MODKBEKBJ-840). Not available for "Not selected" packages (UIEH-1559 — visibility error on Not selected).
- Title visibility (Hidden column) — see Status Values and the next subsection.

### Title+Package (Resource) visibility — "Hide/exclude title" (UIEH-1516 edit, UIEH-1539 view, MODKBEKBJ-831)

- The `Show to patrons` field on the Resource record is replaced by `Hide/exclude title` (en.json `resource.visibility`) with three checkboxes `In Publication Finder`, `In Full Text Finder`, `In MARC export` (en.json `visibility.PF/FTF/MARC`). Info popover text: `If checked, this title will be hidden/excluded in the specified application(s).` plus a `Learn more` button opening a new tab (UIEH-1516).
- View mode: all three checkboxes are disabled; only the saved ones are checked (UIEH-1539).
- Inheritance: if the package has a category hidden, the matching title checkbox is checked and disabled, with the label `(Set by package)` (en.json `visibility.setByPackage`); the package setting overrides the title's own selection (C1602446, C1602447). Verify on Custom title + Custom package, Managed title + Custom package, Managed title + Managed package (UIEH-1516 verification; C1602443, C1602444, C1602445).
- Backend: reason code `Hidden by customer` is sent when hidden = true, none when false (MODKBEKBJ-831). A custom title that is not in a package has no visibility fields (MODKBEKBJ-831 comment). `visibilityData` was deprecated and dropped (MODKBEKBJ-835, BREAKING; UIEH-1516 dev notes). GET `/eholdings/titles` returns `visibility[]` only on resources when `include=resources`; the title itself has none (MODKBEKBJ-834).
- List indicators: Titles accordion row `Title is set to hide` (en.json `titlesList.hidden`); Resource banner `(All titles in this package are hidden)` (`resource.visibilityData.isHidden`); hover text combinations — C736715 (UIEH-1522, UIEH-1592). Known defect noted in UIEH-1539 comments: `(Set by package)` was missing in one verification round; a separate story covers the `Hidden` label text.
- Package edit for `Not selected` packages: `Add the package to holdings to customize package settings.` (en.json `package.visibility.notSelected`); backend returns 422 if a not-selected managed package carries visibility, auto-select titles, custom coverage or token (Karate `packages.feature`).

## Key Business Rules for Test Cases

> Every rule tagged with source: (cases) = confirmed by ≥3 case titles/steps; (github) = from source code/translations; (jira) = from story/bug descriptions.

1. **EBSCO is the only supported external KB** — without valid KB credentials in Settings, eHoldings shows no data (docs.folio.org ERM/eHoldings `_index.md` 'Currently EBSCO is the only supported external KB'; C1404904 precondition 'app returns KB data'; C357013 — user not assigned to any KB gets an access error in the app)
2. **Changes are real-time** — selecting/deselecting a package in FOLIO immediately reflects in EBSCO Holdings Management; proxy/token updates may take a few minutes (docs `_index.md` 'immediately reflected on the other interface'; toast `Package saved. Note: A proxy or token update may take a few minutes…` — en.json, C703)
3. **Cannot delete KB packages or titles** — only custom packages/titles created locally in FOLIO can be deleted; KB content is read-only for deletion (docs `_index.md` custom-package delete section; modal C605986; Karate `packages.feature` 'DELETE Package by id with 204' is the custom-package path)
4. **Select/unselect requires a dedicated capability** — `Data - UI-Eholdings Records - Edit` alone does NOT allow adding/removing holdings; the `Procedural - UI-Eholdings Package-Title Select-Unselect - Execute` capability is also required (package.json `ui-eholdings.package-title.select-unselect.execute` carries `packages.item.put` and `resources.item.put`; C692, C698 list both Edit and Select-Unselect in preconditions)
5. **Custom packages require Name + Content type** — `Name *` is the required field (en.json `package.name.isRequired`; C692, C422012). `Content type` is preselected `Unknown` in the create form (`ui-eholdings/src/components/package/create/package-create.js` `initialValues`) — whether it is a blocking required field is unverified; cases C1404904/C402348 select a value anyway
6. **Custom titles must be linked to a package** — field `Package *` is required; standalone titles cannot exist (en.json `title.package.isRequired` = `Package *`; C387446, C423477)
7. **Proxy hierarchy: Resource > Package > Provider** — `Inherited - {proxy}` is shown when the resource/package inherits (en.json `proxy.inherited`; C692 `Inherited - ezproxY-T`); changing root proxy overrides everything set to inherit (en.json `settings.rootProxy.warning`; docs Settings_eholdings 'Root proxy'). ## Authoring style (measured 2026-07-23)

eHoldings leans **`Functional` (~62%)** with ~35% `Other`, median ~6 steps, `User Journey` ~9%. Cases are compact and behavior-focused: most verify one accordion/filter/search/toast behavior on a Provider/Package/Title record (e.g. "filter retained after editing the Provider", "duplicate custom-package name toast"). Preconditions carry the KB configuration (KB credentials in Settings, a Selected package/title, tags/access-status-types set up) and any Usage-Consolidation setup for cost-per-use cases. Use `Functional` for record/search/filter behavior; `Other` for pure display/label checks. Because the Provider record's own Packages accordion mirrors the Titles accordion, filter/column/sort behaviors are tested on **both** surfaces — don't assume one covers the other.

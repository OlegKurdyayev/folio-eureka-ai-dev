## What is Bulk Edit

Bulk Edit is a FOLIO app for applying the same change to many records in one job. It supports Inventory and Users, with identification by uploaded identifiers or by in-app query. The app includes matching preview, controlled commit, post-commit downloads, and auditable logs. (docs `Bulk Edit/_index.md` intro)

## Key Terms

| Term | Definition |
|---|---|
| Identifier flow | Upload a one-column CSV of record identifiers and match records before editing. (docs `Bulk Edit/_index.md` §Identifier) |
| Query flow | Build and test a query in-app, then run matching and bulk edit from that result set. (docs §Query; C831962) |
| Preview of records matched | Accordion containing matched records and columns selected under Actions > Show columns; shows at most 10 rows (C353561, C380443). |
| Errors and warnings | Accordion showing failed identifier matches or per-record warnings during/after commit; the on-screen list is limited to 10 entries, the full list is in `Download errors (CSV)` (C353561). |
| Bulk edit profile | Reusable profile (Settings) for options/actions, including FOLIO and MARC instance variants. (docs `Settings_bulk_edit.md`; C805763, C805764) |
| Commit changes | Irreversible apply step after confirmation preview (docs `Bulk Edit/_index.md` §Bulk edit by record type; see Key Business Rule 8). |
| Bulk operation type | `UPDATE` (UI "Edit") or `DELETE` (UI "Delete", users only) — schema `operation_type.json`; Logs filter `logs.filter.title.types` = "Bulk operation type" with options `Edit` / `Delete`. |
| Approach | `IN_APP` (form in the app), `MANUAL` (Local / CSV — users only, "Start bulk edit (Local)"), `QUERY` (Query tab) — schema `approach_type.json`; Logs column `columns.logs.approach` = "Editing". |
| Entity type | `USER`, `ITEM`, `HOLDINGS_RECORD`, `INSTANCE`, `INSTANCE_MARC` — schema `entity_type.json`; Logs label for MARC = "Inventory - instances (MARC)" (`logs.entityType.INSTANCE_MARC`). |
| Shadow record (ECS) | Copy of a shared user/instance kept in a member tenant; bulk edit never edits shadow records (MODBULKOPS-339, MODBULKOPS-577, MODBULKOPS-582). |

## Lifecycle / Workflow

Identifier/query to commit flow (docs `Bulk Edit/_index.md` §Identify records, §Preview matching records, §Bulk edit by record type; C353561, C825312):

1. Select record type and identifier (or build query).
2. Upload/test and retrieve matching records.
3. Open Start bulk edit.
4. Configure one or more bulk edit rows.
5. Confirm changes and review preview.
6. Commit changes.
7. Review changed records and warnings.
8. Download matched/changed/errors CSV files as needed.

Bulk operation statuses (backend enum `operation_status_type.json` → UI label from en.json `logs.status.<ENUM>`). Corrected 2026-11-24: "Started" / "Ended" are Logs filter accordions and columns (`logs.filter.startDate`, `logs.filter.endDate`, `columns.logs.startTime/endTime`), not statuses.

| Enum | UI label (en.json key) | When |
|---|---|---|
| NEW | New (`logs.status.NEW`) | Operation created on upload/query. |
| EXECUTING_QUERY / RETRIEVING_IDENTIFIERS / SAVED_IDENTIFIERS | Executing query / Retrieving identifiers / Saving identifiers | Query flow before matching. |
| RETRIEVING_RECORDS | Retrieving records | Matching identifiers to records. |
| SAVING_RECORDS_LOCALLY | Saving records | Matched records stored for preview. |
| DATA_MODIFICATION, DATA_MODIFICATION_IN_PROGRESS | Data modification | Matching done, user editing form. |
| REVIEW_CHANGES, REVIEWED_NO_MARC_RECORDS | Reviewing changes | "Are you sure?" preview. |
| APPLY_CHANGES, APPLY_MARC_CHANGES | Apply changes | Commit running. |
| DELETING_RECORDS | Deleting records (`logs.status.DELETING_RECORDS`) | Bulk delete of users running. |
| COMPLETED | Completed | Finished, no errors. |
| COMPLETED_WITH_ERRORS | Completed with errors | Finished, some records in Errors. |
| FAILED | Failed | Job failed. |
| CANCELLED, SCHEDULED, SUSPENDED | no `logs.status.*` key in en.json | Backend-only; cancel allowed only in some statuses ("Operation with status %s cannot be cancelled", BulkOperationService). |

Steps (`bulk_operation_step.json`): `UPLOAD`, `EDIT`, `COMMIT`, `DELETE`. Starting a step in the wrong status fails with "Step %s is not applicable for bulk operation status %s" (mod-bulk-operations).

## Common Verification Patterns

### Landing page baseline

Action: Open Bulk Edit app.
Expected: Set criteria pane is visible, Identifier tab is active by default, and main pane shows the Bulk edit start state (`Set criteria to start bulk edit`, `Select a record type and then a record identifier.`). (cases — C423643, C375213)

### Record type and identifier gate

Action: Select a record type (for example Users) before choosing a record identifier.
Expected: Identifier selector becomes actionable, while drag-and-drop remains inactive until a concrete identifier is selected; record types are listed alphabetically with none preselected. (cases — C423643, C353561)

### Upload to matched preview

Action: Upload a valid one-column identifiers CSV.
Expected: Retrieval/progress appears (`Uploading <file name> and retrieving relevant data`, progress text `Retrieving`), then Preview of records matched is populated, and Actions menu is enabled. (cases — C423643, C651436)

### Confirm-before-commit

Action: Configure one or more bulk edit rows and click Confirm changes.
Expected: Are you sure? modal opens with preview controls (Keep editing / Download preview / Commit changes). (docs `Bulk Edit/_index.md`; cases — C825312, C831962)

### Commit completion and downloadability

Action: Click Commit changes and wait for completion.
Expected: Changed-records summary is shown and Actions offers Download changed records (CSV) and error CSV when applicable. (cases — C825312, C831962)

### Changing Record identifier resets the whole landing page — even after a completed job

Action: With a matched-records preview (or even a fully committed job) on screen, open the `Record identifier` dropdown and pick a different option.
Expected: The landing page snaps all the way back to its pre-job baseline state, not just clearing the identifier field: record-count label reverts to `Set criteria to start bulk edit`, the `Identifier` tab becomes selected by default again, the main panel reverts to its `Drag and drop or choose file with...` baseline text, the record-type radio buttons re-enable per the user's permissions, and the drag-and-drop area is (re-)enabled. This holds identically whether the change happens before any upload, after a matched-preview, or after a completed Commit changes — there is no partial/preserved state once the identifier changes. (cases — C353650)

## ECS / Multi-Tenant Notes

ECS-specific coverage exists in this subtree (sections include Bulk Edit - ECS, Central tenant, Member tenant). Cases verify that shared and local properties (for example note types, locations, relationships) are resolved correctly by tenant context in both preview columns and output CSV files.

Rules from Jira / code (2026-11-24):
- Central tenant, instances: only **shared** instances are returned by Query; local instances submitted by identifier are reported as not found. Holdings/items of shared instances can still be edited from Central. (MODBULKOPS-533)
- Member tenant, shared instance with no local holdings (no shadow copy): bulk edit must not match it — identifier goes to Errors with `No match found`. (MODBULKOPS-586; related bug UIBULKED-764 "edits shared FOLIO instances from a member tenant, then fails silently", Trillium)
- Shadow copies (users and instances) are never updated; shadow users are filtered out of Query results (Central and member) and reported as `Shadow records cannot be bulk edited.` in the identifier flow. Lists app behaviour is unchanged. (MODBULKOPS-339, MODBULKOPS-577, MODBULKOPS-582)
- Holdings/items can be updated only to locations / loan types that belong to the record's own tenant; otherwise per-record error `... cannot be updated because the record is associated with {tenant} and {value} is not associated with this tenant.` (MODBULKOPS-334, Constants.RECORD_CANNOT_BE_UPDATED_ERROR_TEMPLATE)
- Same identifier present in several tenants (Central, holdings/items) → Errors with `Duplicates across tenants`, upload must not fail (MODBULKOPS-636).
- Optimistic-locking error for holdings/items edited from another tenant has **no** `View latest version` link (cannot link into another tenant's Inventory); same-tenant records keep the link. (UIBULKED-556; Central-tenant query regression UIBULKED-665)
- Central tenant holdings/items identifier lists are the same as in a member tenant (UIBULKED-516).
- Dates (e.g. user Expiration date) display in the tenant time zone, not UTC, on Matching, Are you sure? and Confirmation forms and in files (MODBULKOPS-622, MODBULKOPS-656).
- Bulk edit profiles are tenant-scoped: a profile created in Central is available only in Central, one created in a member only in that member; missing reference data at run time → record not updated, error logged. (UIBULKED-696)
- Local (CSV) user editing is not offered in ECS (Central or member) and not on the Query tab. (UIBULKED-488, UIBULKED-487)
- Bulk delete of users runs in one tenant and deletes only that tenant's users (MODBULKOPS-659); Central-tenant delete via Query is covered by Cypress C1385650, member-tenant open-transactions case by `consortia/bulk-edit/member-tenant/bulk-edit-in-app-users-delete-users-with-open-transactions-in-member-tenant.cy.js`.

## Bulk Delete Users — entirely new feature (confirmed, C1385648)

> Distinct from "Start bulk edit" — deletes matched User records outright rather than editing a field.
> Feature UXPROD-3230; Confluence BULKEDIT page "Umbrellaleaf - Bulk Delete of User Records" (id 2348548103): UAT 2026-09-10..16 passed with no issues; blocking dependencies tested = open loan, fee/fine, manual block; flow Actions → `Start bulk delete` → `Delete`, not-deleted users listed per record in `Errors & warnings`, Logs files differ by identification method (file upload vs query).

- After matching Users (identifier or query flow), the Actions menu offers `Start bulk delete` alongside the usual `Download matched records (CSV)` / `Start bulk edit` / `Select users bulk edit profile`.
- Clicking it opens `Delete user records?` with: a warning banner `{n} user records will be deleted if the Delete button is clicked.` (n = matched count), a note `This action cannot be undone but a file of deleted user records will be available for download in Logs for 30 days.` (the "30 days" reflects the tenant's configured log-retention period, not a hard-coded value), `Cancel` (enabled) and `Delete` (enabled AND focused by default — a single Enter keypress confirms deletion).
- Confirmation screen after deletion shows `{matched} user records match {deleted} user records deleted` — **the deleted count can be LESS than the matched count**: Users with open transactions (e.g. active loans/fees) are silently excluded from deletion even though they matched. Success toast: `{n} user records have been successfully deleted.` (n = actually-deleted count). No `Preview of records changed` accordion appears after a bulk delete (unlike bulk edit). Corrected 2026-11-24: when all records were deleted there is no Actions menu; when some users were NOT deleted, `Errors & warnings` lists each with its reason (e.g. `Open fees/fines`) and the Actions menu offers only `Download errors (CSV)` (`Download matched records (CSV)` is gone). (UIBULKED-27; Cypress C1385650, C1385659)
- `Cancel` in `Delete user records?` closes the modal and leaves the matched preview unchanged (Cypress C1385650 step 7).
- Logs tab entry for the delete job has downloadable files: `File that was used to trigger the bulk edit` (original uploaded CSV) and `File with the matching records` (named `{yyyy-mm-dd}-Matched-Records-{original-filename}.csv`) — there is no "changed records" file, since records were deleted rather than modified.

### Bulk Delete Users — full requirement set from MODBULKOPS-659 (story-sourced; UI part UIBULKED-767)

> Extends the C1385648 behavior above. These items come from the story requirements — verify exact strings on first execution where noted.

- **Two capabilities are required together** to delete user records: `Data - UI-Bulk-Edit Users - Delete` (stripes-testing `capabilitySets.js`; the story calls it "UI-Bulk-Delete Users (delete)") AND the Users delete capability (legacy `ui-users.delete`). Visibility matrix (UIBULKED-99; Cypress C1385649, C1385653, C1385648):
  - Users-Delete + `UI-Users - View` → only `Users` record type, upload + preview + Download matched/errors; NO `Start bulk edit`, NO `Start bulk delete`.
  - Users-Delete + `UI-Users - Edit` → also `Start bulk edit`; still NO `Start bulk delete`.
  - Users-Delete + `UI-Users - Edit` + Users delete → `Start bulk edit` and `Start bulk delete`.
  - Bulk delete permission includes bulk edit of user records; `Start bulk edit (Local)` (CSV) is excluded; bulk edit profiles do not support delete. (UIBULKED-99)
- Backend: `UserDeleteProcessor` calls mod-users-bl `open-transactions` and then deletes through users-keycloak; error text is `Open ` + the non-zero types among `loans, requests, fees/fines, proxies, blocks`.
- `{days}` in `start.delete.modal.note` = configured log retention (default 30 — `LogFilesService.MIN_DAYS_TO_CLEAR_LOG_FILES = 30`; Cypress C1385650 asserts 30). (UIBULKED-26)
- **Deletion criteria come from mod-users, not bulk-ops.** The mod-users delete API (via the `/open-transactions` check) is the source of truth: a user is blocked from deletion if they have open loans, open requests, unpaid fees/fines, unexpired proxies, or manual blocks. Bulk delete does not re-implement these rules — it reports what mod-users returns.
- **Per-record failure logging:** for every matched user that could NOT be deleted, the error log contains the record **UUID** and the **reason** returned by the mod-users API for why it could not be removed. Any other (non-business-rule) failures are reported the same way Bulk edit reports errors.
- **Downloadable files for a delete job (Logs tab), full set:**
  - File that was used to trigger the bulk edit (original uploaded identifiers CSV) — identifier flow.
  - Query flow: `File with identifiers of the records affected by bulk update` (identifiers returned by the query; Cypress C1385650 step 15).
  - **NEW — query flow only:** file with the query used to trigger the job, containing the **user-friendly** query text as shown in the Query builder. File name: `QueryStatement-{jobid}.txt`.
  - File with the matching records (`{yyyy-mm-dd}-Matched-Records-{original-filename}.csv`).
  - File with errors encountered when **retrieving** the records.
  - File with errors encountered when **deleting** the records — named like the bulk-edit commit-errors file: `{yyyy-mm-dd}-Committing-changes-Errors-{name of the file with identifiers or bulk job id}.csv`.
- **ECS: cross-tenant user deletion is NOT supported** — only users associated with the given tenant can be deleted; a bulk delete run in a tenant deletes only that tenant's users. (story — MODBULKOPS-659)

## MARC Field Protection Interaction (confirmed, C569592)

> `Settings > Data import > MARC field protection` rules (field + Ind1 + Ind2 + Subfield + Data, each `*` = wildcard) are honored by Bulk Edit's MARC actions, not just by Data Import.

- A bulk-edit action targeting a field/indicator/subfield/data combination that matches an active protection rule is **silently skipped** — the field is left completely untouched in both the preview (Download preview in MARC/CSV) and the committed result; it is NOT reported as an error or warning.
- Protection is evaluated at the **exact combination level**, not just the 3-digit tag — e.g. a rule protecting `942 0 \ r US` only blocks edits where the existing `$r` value is literally `US`; a `942` field with a different `$r` value would still be editable. Don't assume "field X is protected" means every action on field X is blocked — check the specific indicator/subfield/data the rule specifies.
- Adding a brand-new field/subfield instance that doesn't already exist (e.g. a new `562` occurrence) is unaffected by protection rules for *other* existing fields — protection only prevents modification of matching existing content, not the addition of new content elsewhere in the record.
- This applies uniformly across all MARC bulk-edit actions (Add, Find+Append, Find+Additional subfield, Find+Remove subfield, Find+Remove field, Find+Replace with; `Remove all` was replaced by `Remove field` / `Remove subfield` in Umbrellaleaf — MODBULKOPS-658) — test at least one protected-field case per action type since protection is checked independently per action.

## Item Material Type — "Replace with" action (confirmed, C1348671)

- `Material type` appears under a `Item data` group header in the in-app bulk-edit Options dropdown, positioned between `Administrative data` and `Item notes` groups.
- Unlike most Item-data options (which offer a choice of actions), Material type has exactly **one fixed, read-only action label: `Replace with`** — there is no dropdown of alternative actions for this option — followed by a `Select material type` dropdown populated dynamically from the tenant's configured material types.
- Standard confirm/preview/commit flow applies afterward (Preview of records to be changed shows a "Material type" column with the new value; changed records CSV likewise reflects it).

## Query Builder — "in" / "not in" Operator Value Formatting (confirmed, C477624)

- When `Operator` = `in` or `not in` and the field is a UUID-type column (e.g. `Item — UUID`), the `Value` box accepts a comma-separated paste of multiple UUIDs; the query preview textbox auto-formats them with quotes: `(items.id not in ("{uuid1}","{uuid2}"))` / `(items.id in ("{uuid1}","{uuid2}"))`. Verify the exact quoting/comma placement in the generated query string, not just that the right records come back — malformed quoting here has historically been a bug source.
- `Test query` becomes enabled only once Field + Operator + Value are all populated; while a test is running the button is disabled and shows a `Test query in progress` label with a spinner (query text itself does not re-render during this), and `Cancel` remains available; `Run query` stays disabled until a completed test query exists.

## Holdings → Item Field Recalculation Trigger List (confirmed, C1347164)

Bulk-editing a Holdings record only triggers **Item effective-location/effective-call-number recalculation** for its associated Items when the edit touches one of these exact fields: `permanentLocationId`, `temporaryLocationId`, `callNumber`, `callNumberPrefix`, `callNumberSuffix`, `callNumberTypeId`. Editing any other Holdings field (e.g. a note, or Suppress from discovery) does not trigger Item-side recalculation. This matters most for load-testing scenarios (Holdings with very large Item counts, e.g. 16k+) — pick one of these six fields specifically when the test's purpose is to verify recalculation-at-scale, not an arbitrary Holdings field.

## Read-Only / Authority-Linked Subfield Handling (partially confirmed, needs env re-verification — C663262)

MARC fields linked to an authority record (e.g. `610`, `240` with populated `$0`/`$9`) can still have their non-linking subfields (e.g. `$a`) edited via the normal Find → Replace with / Remove subfield actions, and the resulting Subject/Uniform-title preview columns update accordingly. Whether the linking subfields themselves (`$9` authority UUID, `$0` authority URI) can be independently removed/edited without breaking the authority link was not fully confirmed from this case's available detail — verify in env before asserting either way, and don't assume `$9`/`$0` edits are silently blocked the same way protected fields are (that's a different mechanism).

## MARC Instance Bulk Edit Rules (Jira / docs, 2026-11-24)

- Supported fields `0xx`–`9xx`; `00x` control fields and system-protected `999 ff` are not editable (docs `Bulk Edit/_index.md` §MARC; en.json `layer.marc.error`, `layer.marc.error.protected`). Entering `999` + `f` `f` shows an info icon next to Subfield and keeps `Confirm changes` disabled (UIBULKED-523).
- `Field` must have exactly 3 digits — `Enter a 3-digit field` (UIBULKED-778). Indicator blank is converted to `\` on blur; non-Latin/special characters in In.1/In.2/Subfield keep `Confirm changes` disabled; uppercase subfield → `Please check your input.` (UIBULKED-539, UIBULKED-559).
- Actions: `Add`, `Find` + (`Append` / `Additional subfield` / `Replace with` / `Remove field` / `Remove subfield`). `Remove all` was replaced by `Remove field` (needs Field + 2 indicators; Subfield textbox becomes disabled and its value is cleared) and `Remove subfield` (needs Field + indicators + Subfield; if the field had only that subfield the whole field is removed). The `Subfield` asterisk moved from column header to row level. (MODBULKOPS-658, UIBULKED-590, UIBULKED-775, UIBULKED-774; en.json `layer.options.removeField/removeSubfield`)
- Find/Remove or Find/Replace that empties a subfield removes the subfield; if it was the only subfield the field is removed too, in MARC and in the Instance (MODBULKOPS-499, backport MODBULKOPS-672).
- Subfield order is preserved as entered for new fields and for edited fields; untouched fields keep their order (MODBULKOPS-442).
- Invalid underlying MARC: if only administrative data is edited, the record IS updated; if MARC fields are edited, the record goes to Errors with `Underlying MARC record contains invalid data and the record cannot be updated.`; other records continue (MODBULKOPS-523, C850013).
- Protected fields (Settings > Data import > MARC field protection): bulk edit relies on Data Import; a warning/error is shown only if Data Import reports one (MODBULKOPS-452) — consistent with the "silently skipped" behaviour in C569592.
- `Change note type` for administrative notes and instance-note edits are not supported for MARC instances (UIBULKED-599; mod-bulk-operations messages "Change note type for administrative notes is not supported for MARC Instances.", "Bulk edit of instance notes is not supported for MARC Instances.").
- Source handling: "Instances with source MARC" option + non-MARC records → Are you sure? shows `No instances can be updated because none have source MARC.` when none are MARC (`previewModal.message.empty.notSupported`) or the partly-supported count message (`previewModal.message.empty.partlySupported`) (UIBULKED-584, C663253). "FOLIO Instances" option on MARC/LINKED_DATA records → administrative data supported, other fields not (UIBULKED-595 — see Known Gaps vs LINKED_DATA rule 19).
- MARC instances set as deleted can still be bulk edited (MODBULKOPS-431, MODBULKOPS-416).
- Visual cue: pane title `Bulk edit MARC fields - <b>{fileName}</b>` / `Bulk edit MARC fields query` (en.json `meta.title.uploadedFile.marc`, `meta.query.title.marc`; UIBULKED-594).

## Edge Cases from Bugs (2024-06 → 2026-11)

- Duplicate UUIDs in the uploaded file: must be counted once and reported as duplicates, not shown twice and later failed as optimistic-locking errors (MODBULKOPS-642). Non-unique identifier matches (e.g. former IDs) must go to Errors with `Multiple matches for the same identifier.` and not be updated (MODBULKOPS-641, fixed 2026-08).
- First UUID in a "UTF-8 with BOM" CSV must not be treated as an error (MODBULKOPS-501). Item barcodes with trailing spaces must match (MODBULKOPS-143).
- Parallel uploads with non-UUID identifiers must not hang a single-record job (MODBULKOPS-669); large files (~100K) must upload and show all matched records (MODBULKOPS-590, MODBULKOPS-603, MODBULKOPS-604).
- Confirmation banner must show the actually changed count, not the matched count, when only some records change (UIBULKED-731).
- Editing an item must not clear unrelated item fields; editing a user must not clear `pronouns` (MODBULKOPS-557, MODBULKOPS-545).
- Items with corrupted `circulationNotes.date` go to Errors on matching (MODBULKOPS-568).
- `Reset all` on Identifier and Query tabs is independent per tab; it is disabled until something changes and resets Set criteria plus previews (UIBULKED-751, UIBULKED-757). Logs `Reset all` must clear all filters incl. User (UIBULKED-781). Record count resets when record type/identifier changes (UIBULKED-671).
- `Record identifier` becomes required (asterisk) once a record type is selected (UIBULKED-750).
- `Confirm changes` is enabled after any form change; clicking it with missing required fields highlights them and does not submit (UIBULKED-596, UIBULKED-598, UIBULKED-600..602).
- Statistical codes: Add / Remove / Remove all; `Remove all` cannot be combined with other statistical-code actions ("Combination REMOVE_ALL with other actions is not supported for Statistical code") (MODBULKOPS-389, FolioAbstractDataProcessor).
- `Find` matches a substring for all record types (MODBULKOPS-325). Chained note-type changes are not allowed (UIBULKED-348).
- Holdings permanent location, item permanent loan type and suppress flags cannot be cleared ("Permanent location cannot be cleared", "Permanent loan type cannot be cleared", "Suppress from discovery flag cannot be cleared") (data processors).
- Item bulk edit triggered by holdings UUIDs: bound-with items owned by another holdings are not updated and are reported in Errors (MODBULKOPS-125).
- Users: Local (CSV) approach must keep the expiration time (MODBULKOPS-655); Birth date / Date enrolled must not shift by time zone (MODBULKOPS-656).

## Key Business Rules for Test Cases

1. A bulk edit job can process up to 100,000 records; larger result sets must be narrowed before execution (Query shows the `modal.banner.limit` banner). (cases + docs `Bulk Edit/_index.md` §Identify records; ui-plugin-query-builder en.json)
2. Identifier upload requires a .csv file with exactly one column of identifiers; non-.csv → `Invalid file` modal, malformed → `{fileName} is formatted incorrectly...`, empty → `The uploaded file is empty.` (cases + docs `Bulk Edit/_index.md`; en.json `modal.fileExtensions.*`, `error.incorrectFormatted`)
3. Query flow requires a completed `Test query` before `Run query` is enabled. (cases — C477624; ui-plugin-query-builder en.json `modal.test`, `modal.run`)
4. The Query tab needs `Procedural - UI-Bulk-Edit Query - Execute` in addition to the record-type View/Edit sets; without View/Edit sets for a record type, that type is not offered in Query. (Cypress C376990–C376993, C413364, C413372, C423695, C423696)
5. In-app users editing (`UI-Bulk-Edit Users - Edit`: Email, Expiration date, Patron group) and Local CSV editing (`UI-Bulk-Edit Users Csv - View/Edit`: any field via uploaded CSV) are separate capabilities; Local is offered only on the Identifier tab and not in ECS. (docs `Bulk Edit/_index.md` §Users; UIBULKED-487, UIBULKED-488; Cypress C388491, C388492, C388493)
6. Preview before commit is mandatory; `Commit changes` stays disabled until the Are you sure? preview is populated. (cases; UIBULKED-597)
7. The Are you sure? form offers `Keep editing`, `Download preview in CSV format` (+ `Download preview in MARC format` for MARC) and `Commit changes`. (cases; en.json `previewModal.*`)
8. Commit changes is irreversible in-app; rollback requires a new corrective bulk edit job (no undo endpoint in ModuleDescriptor; cancel only for in-progress statuses). (mod-bulk-operations ModuleDescriptor, BulkOperationService)
9. Multiple fields can be changed in one job by adding rows in Bulk edits; rules are applied in the order of the rows (statistical codes add/remove follow user order). (cases; MODBULKOPS-389)
10. `Clear field` removes the value; required fields cannot be cleared (Item status, Holdings permanent location, Permanent loan type, suppress flags) — rule validation rejects it. (mod-bulk-operations ItemDataProcessor, HoldingsDataProcessor, FolioInstanceDataProcessor)
11. `Add note` appends a note and keeps existing notes; multiple notes of the same type are supported. (docs `Bulk Edit/_index.md` notes tables; UIBULKED-521; Karate holdings/items.feature "add notes")
12. Matching errors do not block updates on successfully matched records; only matched records reach the form. (cases; MODBULKOPS-523, MODBULKOPS-633)
13. Errors and warnings are downloadable independently from changed records (`Download errors (CSV)`; Logs error files for matching and committing). (cases; en.json `start.downloadErrors`, `logs.actions.*ErrorsCsvFile`)
14. Item status can be changed only along the allowed-transition table (e.g. Available → Missing/Withdrawn/..., In process → Missing/Withdrawn only, Lost and paid → Withdrawn only); other targets go to Errors with `New status value "{status}" is not allowed`. (mod-bulk-operations db changelog allowed_item_statuses; MODBULKOPS-563)
15. Query and Logs tabs are capability-gated (`UI-Bulk-Edit Query - Execute`, `UI-Bulk-Edit Logs - View`); without them the tab is not shown. (Cypress C368012, C368013, C413372)
16. **MARC-protected fields are not editable via Bulk Edit** — protection is evaluated at the exact field+indicator+subfield+data combination (not the whole 3-digit tag), and a protected match is silently skipped (no error/warning), leaving that specific field/value untouched while other actions in the same job still apply. (cases — C569592)
17. Logs list every job with ID, Bulk operation type, Record type, Status, Run by, Started, Ended, # of records, Processed, Editing (approach); files are downloadable for 30 days after the job, then removed by the clean-up timer; after that the Actions column shows only an `i` icon whose popup says `Files are unavailable for download because 30 days have elapsed since the date the job was run.` (jobs still without an Ended date, e.g. status New, expire by Started date) while recent jobs show a `...` menu with the file links; the `...` menu is hidden for record types the user has no capability for (e.g. Users logs without UI-Users) (C404368, C411510, C375213, C380562). (cases; en.json `columns.logs.*`; LogFilesService `MIN_DAYS_TO_CLEAR_LOG_FILES = 30`; docs `Bulk Edit/_index.md` §Download a bulk edit log file)
18. Bulk edit profiles in Settings store reusable rules per record type; locked profiles are read-only and cannot be deleted, only duplicated; duplicates are always unlocked. (cases; UIBULKED-661, UIBULKED-663, UIBULKED-711; docs `Settings_bulk_edit.md`)
19. **Bulk edit of instances with source `LINKED_DATA` is entirely unsupported** — such instances are always routed to Errors & warnings with a dedicated reason string, for both Identifier and Query flows; they never appear in Preview of records matched. (cases — C651537)
20. **MARC instances with a missing or stale (`OLD` status) underlying SRS record, or an invalid/short `008` field, cannot be matched for MARC-flow bulk edit** — each produces its own specific Errors & warnings reason and the Instance ends up with "0 instance records matched" if that's the only record in the batch. (cases — C692112, C850013)
21. **Optimistic-locking conflicts on Commit produce a per-record error (not a silent overwrite and not a whole-batch abort)** — the specific record shows `The record cannot be saved because it is not the most recent version...` with a link to the live record; other records in the same job still commit normally. Applies to Instances (incl. their SRS/MARC counterpart, which is also NOT updated on this error — the whole Instance+SRS pair updates atomically or not at all) and to Holdings. (cases — C808444, C468224)
22. **Bulk Delete (Users) is a separate, irreversible action from Bulk Edit** — reachable from the same Actions menu after matching, with its own confirmation modal and its own Logs file set; deleted-count can be less than matched-count when some matched Users have open transactions blocking deletion. (cases — C1385648)
23. **Item effective-location/call-number recalculation after a Holdings bulk edit is scoped to six specific Holdings fields** — `permanentLocationId`, `temporaryLocationId`, `callNumber`, `callNumberPrefix`, `callNumberSuffix`, `callNumberTypeId`; editing any other Holdings field does not cascade to Items. (cases — C1347164)
24. **Changing the `Record identifier` dropdown always fully resets the Bulk Edit landing page to its pre-job baseline**, regardless of what stage the previous job had reached (unstarted, matched-preview only, or fully committed) — there is no "are you sure you want to discard" gate on this action, and no in-between partial-reset state. (cases — C353650)
25. **Bulk delete of users requires two capabilities together** (`Data - UI-Bulk-Edit Users - Delete` + the Users delete capability, legacy `ui-users.delete`; with only Users View/Edit the `Start bulk delete` action is hidden — C1385649, C1385653); the deletion criteria are enforced by mod-users (open loans/requests, unpaid fees/fines, unexpired proxies, manual blocks) so blocked users are excluded with a per-record UUID + reason in the deletion-errors log; in ECS, only users of the tenant the job runs in can be deleted. The query-triggered variant additionally produces a `QueryStatement-{jobid}.txt` file with the user-friendly query. (story — MODBULKOPS-659, UIBULKED-767)

26. **DCB-type users are never bulk edited** — excluded from matching and reported as `Bulk edit of user records with their type set to DCB is not supported.` in identifier and query flows, ECS and non-ECS. (MODBULKOPS-633)
27. **Set records for deletion** needs `UI-Inventory Instance Set-Records-For-Deletion - Execute`, sets staff + discovery suppress true (MARC: SRS deleted, LDR/05 `d`), only on the instance, and cannot be combined with suppress = false in one job. (MODBULKOPS-299, UIBULKED-690; Cypress C831964, C889718; C831962; Karate instances.feature)
28. **MARC field rules** — `Remove field` needs Field + both indicators; `Remove subfield` also needs Subfield and removes the field if it was the only subfield; `Field` must be 3 digits; emptying a subfield via Find/Remove or Find/Replace removes it (and the field if empty); subfield order is preserved; invalid underlying MARC blocks only MARC-field edits (admin-data edits still update). (MODBULKOPS-658, UIBULKED-775, UIBULKED-778, MODBULKOPS-499, MODBULKOPS-442, MODBULKOPS-523)
29. **ECS rules** — Central edits only shared instances; shadow users/instances are never edited (`Shadow records cannot be bulk edited.`); member-tenant shared instances without a shadow copy give `No match found`; holdings/items accept only their own tenant's locations/loan types (per-record error); optimistic-locking errors for other-tenant records have no `View latest version` link. (MODBULKOPS-533, -577, -582, -586, -339, -334; UIBULKED-556; C825312)
30. **Duplicate identifiers are reported, not silently processed** — duplicates counted once, non-unique matches -> `Multiple matches for the same identifier.`, ECS cross-tenant duplicates -> `Duplicates across tenants`. (MODBULKOPS-642, -641, -636)
31. **Item `Material type` and holdings/item Statistical code** are in-app options; Material type has only `Replace with` (required, from Settings > Inventory > Material types); Statistical code `Remove all` cannot be combined with other statistical-code actions. (MODBULKOPS-654, MODBULKOPS-389)
32. **Profile lock is enforced by the backend** — update/delete of a locked profile or locking one requires `bulk-operations.profiles.item.lock.execute`; profiles are tenant-scoped in ECS. (ProfileService.java; UIBULKED-696)
33. **`Reset all` is per tab** (Identifier / Query / Logs), disabled until a change, and returns the tab to default. (UIBULKED-751, UIBULKED-757, UIBULKED-781)
34. **Dates are shown and exported in the tenant time zone** (Expiration date, Birth date, Date enrolled) across Matching, Are you sure?, Confirmation and files. (MODBULKOPS-622, MODBULKOPS-656)
35. **Preview and error lists on screen are capped at 10 rows/entries**; full data is in the downloaded CSV files. (cases — C353561, C380443)

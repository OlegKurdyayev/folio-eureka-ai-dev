## What is Eureka

Eureka is the FOLIO platform architecture that replaces Okapi. API traffic goes through **Kong** (API gateway); authentication/authorization is delegated to **Keycloak** (one realm per tenant); each backend module runs behind a **sidecar** that validates the JWT and the caller's permissions. Platform-level lifecycle is handled by manager services: **mgr-tenants** (tenants ⇄ Keycloak realms), **mgr-applications** (application descriptors), **mgr-tenant-entitlements** (which applications a tenant is entitled to).

The FOLIO-facing consequences that matter for test design: legacy *permissions/permission sets* are replaced by **capabilities / capability sets / authorization roles**; a FOLIO user must be *promoted* to an **auth user** (Keycloak record) before it can log in or receive roles/capabilities; sessions are governed jointly by Keycloak realm settings (fixed-length session) and `stripes.config.js` (idle session); and in ECS every tenant is a separate Keycloak realm, which drives two different login UXs.

This is a *platform* area, not a single app: cases live under Settings > Authorization roles / Authorization policies, the Users app, Consortium manager, and login/session flows that have no app of their own.

## Key Terms

| Term | Definition |
|---|---|
| Kong | API gateway; all API calls go to `<Kong base URL>/...` with header `x-okapi-tenant`. |
| Keycloak | Identity provider. One **realm per tenant**, named after the tenant name/id. Admin console at `<Keycloak base URL>/admin/master/console`. |
| Sidecar | Per-module proxy that validates tokens and capability-based access before the request reaches the module. |
| Capability | Atomic permission unit: `<Type> - <Resource> - <Action>`, where Type ∈ Data / Settings / Procedural. |
| Capability set | Bundle of capabilities; assigning the set implicitly selects its capabilities. |
| Authorization role | Named container of capabilities/capability sets, assignable to users. Types: REGULAR / DEFAULT / CONSORTIUM. |
| Authorization policy | Keycloak policy object; a per-user policy `Policy for user: <name>` is auto-created with `source = SYSTEM` when capabilities are assigned directly to a user. |
| Auth user / Keycloak record | The Keycloak-side representation of a FOLIO user. Created by `POST /users-keycloak/users` or by promotion (`POST /users-keycloak/auth-users/{userId}`). |
| Entitlement | Link between a tenant and an application version; drives which apps/capabilities exist in that tenant. |
| Default role | Role created by an application's entitlement (e.g. "Acquisition Administrator", "Check-in All", `default-system-role-mod-circulation-bff`); `Type = Default`. |
| Central / Member tenant | ECS roles of tenants; each has its own Keycloak realm and its own entitlements. |
| Affiliation | User's membership in a tenant. The **primary** affiliation is the tenant the user was created in and the tenant they land in after login. |
| RTR | Refresh Token Rotation — stripes-core rotates `folioAccessToken` / `folioRefreshToken` via `POST /authn/refresh`. |
| FLS | Fixed-Length Session — hard session cap coming from Keycloak realm session settings. |

## Architecture / Record Hierarchy

```
Keycloak (per-tenant realm)                 Kong (gateway)  ->  sidecar  ->  module
  realm = <tenant name>                       header: x-okapi-tenant: <tenant>
  ├─ clients: <tenant>-application (login theme, SSO), password-reset-client
  ├─ realm roles  = FOLIO authorization roles (incl. default/system roles)
  ├─ realm settings > Sessions = fixed-length session limits
  └─ users        = auth users (a subset of FOLIO users)

Tenant (mgr-tenants)
  ├─ secure: true|false   (immutable after creation)
  ├─ entitlements (mgr-tenant-entitlements) -> applications (mgr-applications)
  │     └─ each entitled application supplies capabilities, capability sets, default roles, system users
  └─ users (mod-users / mod-users-keycloak)
        ├─ user record: type = staff | patron | shadow | system; username (required for staff)
        ├─ auth user (Keycloak record)  <- required for login / roles / capabilities
        ├─ credentials (mod-login-keycloak)
        ├─ authorization roles  -> capability sets -> capabilities
        └─ per-user policy "Policy for user: <name>" (source = SYSTEM)

ECS: Central tenant + N member tenants, each a full stack of the above.
     Shared (CONSORTIUM) roles are pushed from Central to members via Consortium manager.
```

## Login — non-ECS

Flow (single tenant, Keycloak-hosted login):

1. Open the environment URL → login screen with **Username**, **Password** fields and **Log in** button. If `okapi.authnUrl` is configured and `config.tenantOptions` holds exactly one entry, stripes-core redirects straight to that realm's OIDC endpoint: `<authnUrl>/realms/<tenant>/protocol/openid-connect/auth?client_id=<clientId>&response_type=code&redirect_uri=<uri>&scope=openid` [from source].
2. Submitting credentials → `GET /authn/token?code=...`. Response body contains **only** `accessTokenExpiration` and `refreshTokenExpiration`; the tokens themselves arrive as cookies **`folioAccessToken`** and **`folioRefreshToken`**. The access token must never appear in the response body [confirmed C423957].
3. `GET /users-keycloak/_self?expandPermissions=true` returns 200 with a `permissions` array derived from the user's capabilities — whether they were assigned directly or through a role [confirmed C589233]. Permissions belonging to an **unentitled** application are not returned [C1322895].
4. FOLIO welcome page; top navigation bar shows only apps the user has capabilities for; the user's first and last name appear in the profile area, top right.
5. Deep links survive login: opening `<env>/inventory` unauthenticated → login → the Inventory main page opens. After a *manual* logout the next login lands on the welcome page, not the previous app [C451519].

Constraints / notes:
- **A Keycloak record and credentials are prerequisites.** A FOLIO user created with `POST /users` alone cannot log in until it is promoted (`POST /users-keycloak/auth-users/{userId}`) or given credentials (`POST /authn/credentials`, which creates the Keycloak record when a username is present) [C451626, C451631].
- If **Kong is unavailable** or `*/authn/token?code=*` is blocked, login ends on a page with header "Logging out" and a "Log out" button — not on an app page [C630447].
- SSO: when the tenant's `<tenant>-application` client uses a Keycloak theme whose name contains `sso-only`, the native login form is suppressed — only the SSO button(s) are shown, and username/password fields plus the "Sign in with" / "Or sign in with" text are absent [C543873].
- Legacy permission UI is gone: no "User permissions" accordion on the user record, no "Permission sets" under Settings > Users, no "I can haz endpoint" / "Permissions inspector" under Settings > Developer [C442842, C633353]. Settings > Developer > "I can haz capabilities?" maps a permission name/displayName to its capability or capability set [docs `Settings_Authorization-roles.md`; Confluence "Roles Management with Eureka"].
- Keycloak login page (all layouts):
  - "Username" and "Password" carry a required asterisk, rendered as `Username *` / `Password *` [KEYCLOAK-130; C1563889].
  - The "Or sign in with" text appears only when an SSO identity provider is configured [KEYCLOAK-128].
  - The logo's alt text is the realm "Display name" when set, otherwise the tenant name [KEYCLOAK-127; C1574516].
  - The `<html>` element has a `lang` attribute because new realms get Internationalization on (default locale `en`) and existing realms are migrated [MGRTENANT-110, KEYCLOAK-121].
- Login failure responses: `POST /authn/login` and `/authn/login-with-expiry` return **401** with no `folioAccessToken`/`folioRefreshToken` cookies for both a wrong password and an unknown username [Karate `mod-login-keycloak/features/verify-login.feature`, `verify-login-with-expiry.feature`; MODLOGINKC-72]. The message must not reveal which of the two was wrong [STCOR-703, KEYCLOAK-101].
- Users cannot edit their own Keycloak user attributes: every tenant realm's `unmanagedAttributePolicy` is `ADMIN_EDIT` [MGRTENANT-95].

## Login — ECS

In ECS every tenant is its own realm, so authentication must be pointed at a realm. Two UXs exist; which one appears is a **configuration** choice in `stripes.config.js` (`config.tenantOptions`), not a user choice [from source `AuthnLogin.js`].

### The two ECS login forms

| | **Single-UX login** (one login form) | **Tenant-dropdown login** (pre-login tenant selection) |
|---|---|---|
| Config | `config.tenantOptions` undefined or exactly **1** entry (the central tenant); falls back to `okapi.tenant` / `okapi.clientId` | `config.tenantOptions` holds **more than one** entry (central + members), each with its own `name`, `displayName`, `clientId` |
| First screen | Login form immediately (browser is redirected to the single realm's OIDC auth URL) | **Tenant/library selection screen**: `OrganizationLogo`, a **"Tenant/Library"** select whose default option reads **"Select your tenant/library"**, and a **"Continue"** button that stays **disabled** until a tenant is chosen |
| Realm used to authenticate | Always the central tenant realm | The realm of the tenant picked in the dropdown |
| Auth URL | `.../realms/<central>/protocol/openid-connect/auth?...&scope=openid` | `.../realms/<selected tenant>/protocol/openid-connect/auth?...&scope=openid&isConsortium=true` |
| Where the user lands | Their **primary affiliation** tenant, regardless of where they typed credentials — a user created in a member tenant logs in through the central URL and lands in the member tenant [C1030032 steps 6-11, C1292039 step 5] | The tenant selected on the first screen; the active affiliation after login equals that tenant [C740245 step 5] |
| Extra UI on the login form | none | **"Return to tenant/library selection screen"** link below the "Log in" button [from cases C740245]; still present after a failed login attempt [KEYCLOAK-51] |
| Deep-linking | `<env>/inventory` → login → Inventory [C451520] | The login URL *with the tenant preselected* can be copied and reopened (including in Incognito) and still shows the selected tenant's login form [C740245] |
| Tenant options list | n/a | Sorted by `sortableName` → `displayName` → `name`; labels show `displayName` when present [STCOR-965, STCOR-899] |
| Typical use | consortium with a single shared entry point / "one FOLIO login for everyone" | consortium where each library authenticates against its own realm |

> `SelectAndDispatchTenant` is a related component that renders a "Select your tenant/library" **select inside** the native (non-Keycloak) login form when `tenantOptions` has more than one entry, and renders `null` for central-tenant-only authn [from source]. It is not referenced from `Login.js` on `main` — see Known Gaps before writing a case against it.

Other ECS login/logout behavior:
- Affiliation switching is done from the user profile section in the top-right: **"Switch active affiliation"** → **"Select affiliation"** modal with a **"Consortium members"** dropdown → **"Save & close"**. The selected tenant name is then shown in the profile section [C423958, C449377].
- Switching affiliation triggers `GET /entitlements/{tenantId}/applications` with `x-okapi-tenant` = that tenant, so the app list in the top bar is per-tenant [C449377].
- A user whose only affiliation is a member tenant logs in and lands in that member tenant; logging out returns them to the login screen [C430269].
- Re-login destination depends on **how** the session ended: after a *session timeout* the user returns to the exact record/page and tenant they were on; after a *manual logout* they land on the FOLIO welcome page at the initial URL in their primary tenant [C1292039].
- Session timeouts are per-tenant realm settings, so Central and Member can expire at different times; the counter keeps running across an affiliation switch and is not restarted by it [C1292039 steps 10-11, C1453684, C1453689].

## Session management (RTR, idle session, fixed-length session)

Two independent timers:

| | Idle session | Fixed-length session (FLS) |
|---|---|---|
| Source of truth | `stripes.config.js` → `config.rtr.idleSessionTTL`, `config.rtr.idleModalTTL`, `config.rtr.activityEvents` | Keycloak: realm → **Realm settings > Sessions** → "SSO Session Idle", "SSO Session Max", "Client Session Idle", "Client Session Max" (set all four to the same value to define it) |
| Warning UI | **Modal** — title "Your session will expire soon!", text "Time remaining: MM:SS", **"Keep working"** button | **Message banner** below the top navigation bar — "Your session will end soon! Time remaining: MM:SS" |
| Warning lead time | `idleModalTTL` before expiry | `config.rtr.fixedLengthSessionWarningTTL` — **1 minute** in practice |
| Dismissing the warning | "Keep working" **or** ESC resets the idle timer; the countdown reaching zero after dismissal does nothing | Cannot be dismissed or extended — expiry is a hard cap |
| On expiry | `POST /authn/logout` (204) → screen with "Your session expired due to inactivity." + **"Log in again"** link | Redirect to the logout page with a **"Log in again"** button |
| After re-login | The page open before expiry is restored (unsaved form input is cleared) | Same — the page is restored, form fields are back to defaults |

Additional confirmed behavior:
- Token rotation: while the user works, `POST /authn/refresh` returns 201 and both cookie expirations move forward. Rotation keeps working in a second tab after the tab used to log in is closed [C514952].
- FLS timers are **per session**, not per user: two browsers logged in as the same user expire independently, each restoring its own page after re-login [C506678].
- The FLS countdown reflects *actual* remaining session time — it must not restart on page reload, on opening the same page in a second tab, or on switching affiliation [C1453684, C1453685, C1453689, C1453712].
- Tabs are synchronized through a BroadcastChannel: activity in one window pings the idle timers of the others [from source `SessionEventContainer.js`].
- Logout: user profile menu → "Log out" → logout screen with "You have logged out." + "Log in again". With `confirmLogout = false` (default) there is no confirmation step [C436889].
- `config.rtr` defaults when `stripes.config.js` sets nothing: `idleSessionTTL` **4h** (was 1h before STCOR-962), `idleModalTTL` **1m**, `fixedLengthSessionWarningTTL` **1m**, `activityEvents` `['keydown', 'mousedown']` [source `stripes-core/src/components/Root/constants.js`].
- The idle-session modal is **not** shown when the fixed-length session will end before the idle modal's countdown would — only the FLS banner appears [STCOR-884].
- A refresh (`POST /authn/refresh`) is sent *before* `POST /authn/logout` on manual logout, idle expiry and FLS expiry [STCOR-1068; C1464078, C1464261, C1464262]. After the logout page opens no further `/authn/refresh` is sent, and re-login returns the user to the page they were on [STCOR-1108].
- New tenant realms are provisioned with RTR already configured and session defaults of **18 h** for SSO Session Idle/Max and Client Session Idle/Max, with a **5 min** access-token lifespan [MGRTENANT-76, MGRTENANT-55]. Cases that need a short FLS still override these four realm values (see Common Verification Patterns).
- Entitlement polling: stripes-core polls the tenant's entitlements (default every 15 min) and shows a banner "FOLIO has been updated." + link "Click here to reload." when they change (keys `stale.warning`, `stale.reload`) [STCOR-780].
- First-open failure text: "Sorry, there was an error during initialization. Please try again." (`init.error`) — STCOR-1066/STCOR-1105 fixed spurious occurrences on first login [source en.json].

## Password management — constraints

- **Username is mandatory for authentication.** Any attempt to create a Keycloak record, credentials, or a role/capability assignment for a user without a username fails with `"User without username cannot be created in Keycloak"` (400 via `POST /users-keycloak/auth-users/{id}`, 500 via `POST /authn/credentials` and `POST /authn/update`) [C451626, C451631, C594518, C627403]. `patron`-type users do not require a username — the field's required marker disappears when User type is switched to patron [C1051455].
- Credentials APIs: create `POST /authn/credentials` (201, creates the Keycloak record when a username is present); change `POST /authn/update` with `password` + `newPassword` (204); unknown username → 404 `"Failed to find user by name: username = <...>"` [C451626, C594518].
- Assignments require a Keycloak record: `POST /roles/users`, `POST /users/capabilities`, `POST /users/capability-sets` return **404 "Keycloak user doesn't exist"** for non-auth users [C627444, C627445].
- **Reset-password link**: Users app → user → Actions > Edit → **"Send reset password email"** link next to the Username field → "Reset password email sent" modal shows the URL, matching the `link` property in the `POST /users-keycloak/password-reset/link` response. Requires `Procedural - UI-Users Reset Password - Execute` **and** `Procedural - Users-keycloak Password-Reset-Link Generate - Execute` [C434077].
- The link's base URL is configurable at runtime: `PUT <Kong>/base-url` with `{"baseUrl": "..."}` changes the host used in generated links [C1322906]. UI path default `/reset-password` [from source].
- Link lifetime: `RESET_PASSWORD_LINK_EXPIRATION_TIME` = **24 hours** (`KC_PASSWORD_RESET_TOKEN_TTL` = 86400 s, max 4 weeks) and the link is **single-use** — reuse or expiry shows "Your choose password link expired or has already been used…" [from source].
- Password rules enforced on the "Choose a password" page [from source `stripes-core/en.json`]: minimum 8 characters; both lower- and uppercase letters; ≥1 digit; ≥1 special character; must not contain the username; no keyboard sequence; no repeated character in a row; no whitespace (and no consecutive whitespace); not commonly-used/compromised; not one of the last ten passwords.
- Account lockout and disabled accounts are Keycloak-side: an **inactive** user entering the correct password sees `"Account is disabled. Contact your administrator"` above the Username field (Umbrellaleaf onward; earlier releases showed "Invalid username or password.") [C1030031, C1030032 — KEYCLOAK-101]. Brute-force strings "You have entered the wrong username or password for the third time…" / "For security purposes, your account has been locked…" exist in stripes-core but are not covered by any case [from source].
- Migration/system-user specifics: `DEFAULT_PASSWORDS_ON_MIGRATION=false` (migrated users get no credentials unless enabled); generated system-user passwords are 32 chars [from source].
- Users with uppercase letters in the username (including migrated ECS users whose primary affiliation is a member tenant) can log in [KEYCLOAK-87, MODUSERSKC-119].
- A user whose `expirationDate` passes becomes inactive in Keycloak too and can no longer log in [MODUSERSKC-154].
- Reset-password and account-activation emails carry a working "request a new link" URL pointing at the tenant's forgot-password page (`FORGOT_PASSWORD_UI_PATH`, default `/forgot-password`) [MODUSERSKC-180].

### Forgot password / Forgot username (login page links)

- Links "Forgot password?" / "Forgot username?" on the login page (keys `button.forgotPassword`, `button.forgotUsername`) [source stripes-core en.json; C1574453, C1574454].
- Forgot password accepts **username, email or phone**: call to action "Enter your email, username or phone number" (`label.forgotPasswordCallToAction`), placeholder "Enter username, email or phone" (`placeholder.field.forgotPassword`) [STCOR-1020]. Forgot username accepts email or phone: "Enter your email or phone number" / "Enter email or phone" (`label.forgotUsernameCallToAction`, `placeholder.forgotUsername`).
- The input is marked required with an asterisk; an empty submit shows the banner error rather than inline text [STCOR-1091; key `label.missingRequiredField` = "Please fill this in to continue"].
- After submit: "Check your email" (`label.check.email`), "An email has been sent to your email address." (`label.your.email`) and "If you don't receive the email, check your spam, junk, social or other folders. Or contact your FOLIO system administrator." (`label.caution.email`) [source en.json; STCOR-1090].
- Backend: `POST /users-keycloak/forgotten/password` and `/forgotten/username` (no permission required) **always return 204**. When no user or several users match the identifier, no email is sent and the outcome is only logged at WARN, so the UI cannot reveal whether the account exists [MODUSERSKC-111]. In ECS the duplicate check covers users of **all** tenants, including matches on phone/mobile number [MODUSERSKC-83, MODUSERSKC-106].
- Neither request may trigger `/authn/refresh` (`rtrIgnore`) [STCOR-1089, STCOR-1099].

## Tenants, Keycloak records, authorization roles

**Tenants**
- Creating a tenant creates the matching **Keycloak realm**; every tenant-scoped operation happens inside that realm [from source `mgr-tenants`].
- New realms are provisioned with RTR on, 18 h session limits, a 5 min access token, `unmanagedAttributePolicy = ADMIN_EDIT` and Internationalization enabled (default locale `en`). The last two are also migrated, idempotently, onto existing tenant realms at mgr-tenants startup; the `master` realm is excluded [MGRTENANT-55, MGRTENANT-76, MGRTENANT-95, MGRTENANT-110].
- `POST <Kong>/tenants` accepts an optional boolean **`secure`**. Omitted → the field is absent from the response; `true`/`false` → stored and returned; a non-boolean (`"no"`) → 400. `secure` is **immutable**: any `PUT` that adds or changes it returns 400 `"Secure field cannot be modified"`. Tenants can be filtered with `GET /tenants?query=secure=true|false` [C503152, C503153].
- A tenant **cannot be deleted while applications are entitled** to it: `DELETE /tenants/{id}` → 400 "tenant cannot be removed because it has installed applications"; after `DELETE /entitlements` it returns 204 [C895662; MGRTENANT-17].
- Backend admin auth for platform endpoints is a client-credentials token from `POST <Keycloak>/realms/master/protocol/openid-connect/token`; tenant-scoped API auth is `POST /authn/login-with-expiry` with `x-okapi-tenant` [corpus-wide pattern].

**Keycloak records (auth users)**
- `GET /users-keycloak/auth-users/{userId}` → **204** when the user has a Keycloak record, **404 "Not Found"** when not. `POST /users-keycloak/auth-users/{userId}` promotes: 201 for a first promotion, 204 when already promoted, 404 for a random UUID, 400 when the user has no username [C451631, C451632].
- The UI creates records on demand and always asks first:
  - Settings > Authorization roles → role → "Assign/Unassign" → Save → **"Create user records in Keycloak"** modal: "This operation will create new records in Keycloak for the following users: <UUIDs>", Cancel / Confirm. Cancel or ESC assigns **nobody** — users without records are dropped and only the already-promoted user stays assigned; Confirm sends one `POST /users-keycloak/auth-users/{id}` per user (201) and all rows appear [C627395, C627404].
  - Users app → user → Edit → assign a role → Save & close → **"Keycloak user record"** modal: "This operation will create new record in Keycloak for <last name, first name middle name> in the <tenant> tenant." Cancel leaves the role count unchanged [C1347148-C1347151].
- Duplicate emails: with Keycloak's "Duplicate emails" toggle off, promoting a second user with an existing email fails with "Failed to create user records in keycloak for users: <id>: Failed to create keycloak user: userId = <id>, realm = <tenant>"; enabling the toggle makes the same assignment succeed with "Keycloak records created for the following users: <id>" [C889748].
- Deleting a user (`DELETE /users-keycloak/users/{id}`, 204) cascades: user policies, user roles, user capabilities and user capability sets all return empty collections afterwards [C436914; Karate `mod-roles-keycloak/features/user-deletion-cleanup.feature`].
- **Username pre-check (UI)**: if *any* user selected in "Assign/Unassign" has no username, the whole operation is aborted with the error toast "User assignment aborted.  This operation requires all users involved to have a username." (two spaces after the first period). Nobody is assigned and no Keycloak records are checked or created [UISAUTHCOM-103; C1504509; key `assignUnassign.error.username`].
- When several users need Keycloak records and some promotions fail (e.g. duplicate email), the UI still attempts every user and groups the failures in one error ("Failed to create user records in keycloak for users: {users}: {error}") [UISAUTHCOM-68; key `keycloak.records.create.error`].
- Assigning capabilities, capability sets or roles to a user with no Keycloak record **via the API** returns 404 and assigns nothing — promotion happens only through the UI confirmation [MODROLESKC-258; C627444, C627445].
- Expanded role detail: user names in "Assigned users" are plain text, not links, when the viewer has no access to the Users app [UISAUTHCOM-42].
- `GET` and `DELETE /users-keycloak/users` (collection) have been removed; look users up through `mod-users` instead [MODUSERSKC-166, MODUSERSKC-154].

**Authorization roles**
- Role list columns: **Name, Description, Type, Updated, Updated by**. Detail view has "Capabilities" and "Capability sets" accordions with counters, an "Assigned users" accordion, "General Information", and (in ECS/Consortium manager) a "Centrally managed" value [C502978, C446120].
- Role types: **REGULAR** (created by users), **DEFAULT** (created by application entitlement, incl. `default-system-role-*` for system users), **CONSORTIUM** (result of sharing). The UI renders them as `Type = Regular / Default / Consortium`.
- **Default roles are read-only**: the Actions menu offers only "Duplicate" (no Edit/Delete), the direct `/edit` URL renders a blank page, and the API rejects both directions of a type change with 400 `"Default role cannot be created, updated or deleted via roles API."` [C794509, C957370; UISAUTHCOM-66]. The API also refuses to create a role with `type = DEFAULT` or to change a type to or from DEFAULT [MODROLESKC-349, MODROLESKC-338].
- Default roles come and go with entitlements: entitling `app-platform-minimal` creates them in the Keycloak realm; `DELETE /entitlements?purge=true` removes them, restoring the pre-entitlement realm role list [C494090]. Each application's system users get their own default role with the module's capabilities [C784506].
- **Role name**: required, 1–255 characters, must not contain `/` (OpenAPI `pattern "^[^/]+$"`) [source `mod-roles-keycloak/.../schemas/role/role.json`; MODROLESKC-413]. The API returns 400 `validation_error` with message `must match "^[^/]+$"`. The rule also applies to loadable/default role seeding and `PUT /loadable-roles`, though loadable-role *descriptions* may contain `/` [MODROLESKC-418]. In the create/edit form the inline error "Role name cannot contain the "/" character" appears on blur/submit and Save stays disabled [UISAUTHCOM-97; key `form.errors.name.invalidCharacter`]. Save becomes enabled after the first character is typed in Name [UIROLES-170].
- Duplicating a role (Actions > "Duplicate" > "Duplicate role?" modal: "Are you sure you want to create a duplicate of this role **<name>**?") copies capabilities and capability sets but **never** the assigned users. The copy gets `Type = Regular` and the name `<role name> (duplicate) - <locale date-time>`, with `/` in the date replaced by `-` (e.g. `Role A (duplicate) - 7-24-2026, 7:14:03 AM`). Success toast: "The role **<name>** has been successfully **duplicated**"; failure: "There was an error while duplicating the role <name>" [C554636; source `stripes-authorization-components/lib/hooks/useAuthorizationRolesMutation`; UISAUTHCOM-104, UISAUTHCOM-49; keys `crud.duplicateRole`, `crud.duplicateConfirmation`, `authorizationsRoles.duplicate.success|error`].
- Deleting a role with capabilities and users assigned is allowed after confirming the "Delete role" modal ("<role name> will be deleted"); Cancel keeps the record [C446119, C446120]. The role's user assignments are removed with it, and deletion cannot be undone [Confluence "Roles Management with Eureka"].
- **Deleting a role assigned to yourself** opens a second modal "Delete currently-assigned role?" after "Delete role": "**Warning:** The role you are deleting is assigned to you: **<role>** You may lose some privileges if you proceed." with a Confirm button [UISAUTHCOM-102; keys `crud.assignedRoleDeletion`, `crud.deleteAssignedRoleConfirmation`]. Both modals can be suppressed for the rest of the session ("do not show again"), and suppressing the first does not suppress the second (UISAUTHCOM-102 QA comment).
- Capability API details: `GET /roles/{id}/capabilities` marks directly-assigned capabilities `"direct": true` and set-derived ones `"direct": false` (with `expand=true`); `dedup=false` returns an overlapping capability twice (direct + indirect), the default dedups to the `direct` entry, and an invalid `dedup` value returns 400 [C1375886; MODROLESKC-408].
- Capability-set semantics in the UI: checking a capability set auto-checks its capabilities, and unchecking it releases them [C434129, C503019, C1395070, C1395071]. Capabilities auto-checked by a set cannot be unchecked one by one [Confluence "Roles Management with Eureka"]. Capabilities checked individually *before* the set was checked stay checked after the set is unchecked, whether saved or unsaved [UISAUTHCOM-83; C434129, C503019].

**Role editor (create / edit form)**
- "Select application" opens the "Select application" modal. Only capabilities/sets of the selected applications are listed, grouped into Data / Settings / Procedural accordions [Confluence; keys `crud.selectApplication`, `details.data|settings|procedural`]. The modal has a **Status** column and filter (Assigned / Unassigned). "Assigned" means the *saved* role already holds a capability from that application, not the current checkbox state [UISAUTHCOM-108; stripes-testing `selectAppAssignmentOptions`].
- Unchecking an application that contributes selected items shows a warning on "Save & close": "By unselecting <apps>, **N** capabilities and **M** capability sets will also be unselected. Are you sure you'd like to proceed?" with a "Continue" button [UISAUTHCOM-69, UISAUTHCOM-73; C916226, C926156; key `applications.unselect.warning`].
- Unchecking a capability set shows "By unselecting <set>, **N** capabilities will also be unselected.  Are you sure you'd like to proceed?" with a session-scoped "do not show again" checkbox. The choice survives a page refresh and resets on re-login, and the same modal exists in Consortium manager [UISAUTHCOM-98; C1395070, C1395071; key `capabilitySets.unselect.warning`].
- Column-header checkboxes ("Select all {action} capabilities") select a whole action column, but only for the currently selected applications, and leave set-derived capabilities untouched [UISAUTHCOM-40; C624253, C624254; key `columns.header.checkbox`].
- "Show hidden capabilities" checkbox (default unchecked) in the create/edit forms: when unchecked, capabilities/sets with `visible: false` are hidden (`true` and missing both count as visible). The role details pane always hides them and has no toggle [UISAUTHCOM-101; key `form.labels.showHidden`].
- Role-list pane button reads "New" (no "+") [UIROLES-203, STCOR-1093].
- Role create/edit/share requests use a long client timeout (10 min) because sharing to many tenants can take minutes [UISAUTHCOM-59, UISAUTHCOM-81].

**Authorization policies**
- Assigning capabilities directly to a user auto-creates `Policy for user: <name>` with `source = SYSTEM`; a `PUT` that tries to change `source` to `USER` returns 204 but the value stays **SYSTEM** [C514999]. `source` is not user-editable [C514991].
- Policy enums: `type` USER / TIME / ROLE; `source` SYSTEM / USER / CONSORTIUM [source `mod-roles-keycloak/.../schemas/policy/policyType.json`, `sourceType.json`]. Policy toasts exist in stripes-authorization-components ("Policy has been created successfully", "Policy has been updated successfully", "Policy has been shared successfully", plus "could not be …" variants), but shared policies cannot be edited outside Consortium manager [UISAUTHCOM-21, UISAUTHCOM-24].

**`_self` and permissions**
- `GET /users-keycloak/_self` needs a valid access token: 401 without one, 200 with `user` + `permissions` with one [Karate `mod-users-keycloak/features/self.feature`; MODUSERSKC-165]. It returns **all** assigned permissions by default, including those whose capability is `visible: false` [MODUSERSKC-138], plus permissions coming from capability sets [MODUSERSKC-52]. Permissions of applications no longer entitled are dropped [C1322895; MODROLESKC-332].

## ECS / Multi-Tenant Notes

- 78 of 207 cases are ECS (`ECS Enabled = true`), concentrated in Login > Consortia (32029), Users > Consortia (42028) and Consortium manager (Eureka) (40125). `Multi-Tenant` is `false` on **every** case in this subtree — ECS coverage is flagged with `ECS Enabled`, not `Multi-Tenant`.
- Preconditions in ECS cases always state: which tenant each user was created in, the user's affiliations, and the capability sets **per tenant** (they routinely differ — e.g. Consortium-manager and Affiliations sets exist only in Central).
- Only roles that live in the **Central** tenant can be shared: for a role created in a member tenant the "Share to all" option is absent from the Actions menu [C523604].
- Role-name uniqueness for sharing/renaming is **case-insensitive across all member tenants**; the error toast names the offending members. Sharing succeeds only after the clashing names are made unique [C692096, C1030054, C1263896].
- A shared role in a member tenant carries the same capabilities/sets but has **no assigned users** there; members' own like-named local roles keep their own users and capabilities untouched [C692096].
- Sharing with only Central selected in "Select members" still converts the role to CONSORTIUM; in member tenants the role is then visible but has no "Actions" button for users lacking member-tenant capabilities [C523612].
- The "User roles" accordion shows an **"Affiliation" dropdown only for `staff` users** (defaulting to the primary affiliation); it disappears for `patron` users, and switching type shows the "Changing user type?" confirmation modal [C1051455].
- Assigning a role in Central vs Member decides which realm gets the Keycloak record; the "Keycloak user record" modal names the tenant, and assignment order (Central-then-Member vs Member-then-Central) is an explicit test dimension [C1347148-C1347151].
- Compare-users / compare-capabilities views in Consortium manager query `/users` with `limit=4000` and include only `staff`, `shadow` and `system` users — `patron` users are excluded [C1009047].
- Shared (centrally managed) roles and policies can be viewed in member-tenant Settings but not edited or deleted there; edits happen only in Consortium manager with Central selected [UISAUTHCOM-20, UISAUTHCOM-21].
- When a shared role holds capabilities whose application is not entitled in a member, sharing still succeeds: those capabilities are skipped, so the role legitimately has fewer capabilities in that member than in Central [MODROLESKC-297; C722382].
- Renaming a shared role to a name already used in any member tenant is blocked with an error; sharing a Central role whose name exists in a member is blocked by an inline "Name is already in use at one or more member libraries" error with Save disabled [UISAUTHCOM-90, UISAUTHCOM-86; key `role.share.error.duplicate`].
- Role names containing the word "and" can be shared (CQL-escaped) [UISAUTHCOM-88]. QA noted on UISAUTHCOM-86/88 that names containing `&` or `#` could not be shared — see Known Gaps.
- A shared role can be duplicated only in Central via Consortium manager; there is no Duplicate action for shared roles in member tenants or in Settings [UIROLES-127 comments; C552454].
- The "Select user ({tenant})" modal title names the tenant the assignment applies to [UISAUTHCOM-37].
- "Forgot password/username" in ECS searches all tenants, and duplicate contact info anywhere suppresses the email [MODUSERSKC-83, MODUSERSKC-106].
- Users with multiple affiliations and roles in every tenant may leave shadow users behind when deleted from the primary tenant (Won't Do) — do not assert full cross-tenant deletion [MODUSERSKC-92].

## Key Business Rules for Test Cases

> One rule per line, each with its source (TestRail C-id, Jira key, repo path or Confluence). Rules 1–30 come from the 2026-08-13 build (case IDs added 2026-11-24); rules 31+ were added in the 2026-11-24 refresh.

1. A FOLIO user cannot log in, hold roles, or hold capabilities without a Keycloak record (auth user); promotion comes first (C451626, C451631; Confluence "Roles Management with Eureka").
2. A user without a username can never get a Keycloak record; every such attempt fails with "User without username cannot be created in Keycloak" (C451626, C451631, C594518, C627403; Karate `auth-users.feature`).
3. `POST /authn/credentials` with a username creates both the credentials and the Keycloak record, and the user can log in immediately (C451626; MODLOGINKC-17).
4. Role/capability assignment APIs return 404 "Keycloak user doesn't exist" for non-auth users; the UI instead offers to create the records and assigns nobody if the confirmation is cancelled (C627444, C627445, C627395, C627404; MODROLESKC-258).
5. The login response never carries the access token in its body; tokens arrive as `folioAccessToken` / `folioRefreshToken` cookies (C423957).
6. `GET /users-keycloak/_self?expandPermissions=true` returns permissions from directly assigned **and** role-derived capabilities, and drops those of unentitled applications (C589233, C1322895; MODROLESKC-332).
7. Deep-linked URLs are restored after login; after a manual logout the user lands on the welcome page instead (C451519, C451520).
8. The idle-session warning can be dismissed ("Keep working" or ESC), which resets the timer; the fixed-length session warning cannot be dismissed and always ends in logout (idle/FLS cases of the 2026-08-13 build — C-ids not recorded there; stripes-core `SessionEventContainer.js`, `KeepWorkingModal.js`).
9. The fixed-length session countdown shows real remaining time: a page reload, a new tab or an affiliation switch does not restart it (C1453684, C1453685, C1453689, C1453712; STCOR-1087).
10. Fixed-length sessions are per session/browser, not per user (C506678).
11. After a session-timeout logout the user returns to the same page **and tenant**; after a manual logout, to the welcome page in their primary affiliation (C1292039; STCOR-1108).
12. In ECS the landing tenant is the user's primary affiliation with the single login form, and the selected tenant with the tenant-dropdown login (C1030032, C1292039, C740245; stripes-core `AuthnLogin.js`).
13. The ECS tenant-selection screen keeps "Continue" disabled until a tenant is picked, and its URL can be reused with the tenant preselected (C740245; stripes-core `AuthnLogin.js`).
14. With an `sso-only` Keycloak theme, native username/password login is unavailable for that tenant (C543873; KEYCLOAK-19).
15. Password-reset links are generated per user, expire after 24 hours, are single-use, and their base URL is configurable through `PUT /base-url` (C434077, C1322906; mod-users-keycloak README).
16. The legacy permission UI (User permissions accordion, Permission sets, Permissions inspector) is absent on Eureka (C442842, C633353).
17. Default roles cannot be created, edited or deleted: the UI offers only "Duplicate" and the `/edit` URL is blank; the API returns 400 (C794509, C957370; UISAUTHCOM-66).
18. Default roles are created and purged with application entitlements; each application's system users get a default role carrying that module's capabilities (C494090, C784506).
19. Duplicating a role copies capabilities and capability sets but never assigned users (C554636; Confluence "Roles Management with Eureka").
20. Deleting a user removes its policies, roles, capabilities and capability sets (C436914; Karate `user-deletion-cleanup.feature`).
21. Assigning capabilities directly to a user creates a `Policy for user: <name>` policy with `source = SYSTEM`, and the source cannot be changed to USER (C514999, C514991).
22. A tenant's `secure` flag is set only at creation and can never be modified (C503152, C503153).
23. A tenant cannot be deleted while it has entitled applications (C895662; MGRTENANT-17).
24. Only Central-tenant roles can be shared; sharing sets Type = Consortium and "Centrally managed" = Yes (C523604, C523612; Confluence).
25. Sharing or renaming a role fails when the name already exists (case-insensitively) in any member tenant, and the error names those members (C692096, C1030054, C1263896; UISAUTHCOM-90).
26. A shared role in a member tenant starts with no users assigned there: sharing never carries user assignments (C692096).
27. The "Affiliation" dropdown in "User roles" exists only for staff users (C1051455).
28. `patron` users are excluded from user/capability comparison views, which request `/users` with `limit=4000` (C1009047).
29. Capability sets and their capabilities are selected and deselected together in the role editor (C434129, C503019, C1395070, C1395071).
30. `GET /roles/{id}/capabilities` dedups direct and set-derived duplicates by default; `dedup=false` returns both entries and an invalid value returns 400 (C1375886; MODROLESKC-408).
31. A role name must not contain `/`: the API returns 400 `must match "^[^/]+$"`, and the UI shows "Role name cannot contain the "/" character" with Save disabled, on both create and edit (MODROLESKC-413, UISAUTHCOM-97; `role.json`, `form.errors.name.invalidCharacter`).
32. The `/` restriction also applies to loadable/default role seeding and `PUT /loadable-roles`; loadable-role descriptions may contain `/` (MODROLESKC-418).
33. Duplicate role names have the form `<name> (duplicate) - <date-time>`, with `/` in the date replaced by `-`, so duplication never trips the `/` rule; the copy is Type = Regular (UISAUTHCOM-104, UISAUTHCOM-49; `useAuthorizationRolesMutation.js`).
34. A role's type cannot be set to DEFAULT on create, nor changed to or from DEFAULT on update (MODROLESKC-349, MODROLESKC-338; C957370).
35. If any user selected for a role has no username, the UI aborts the whole assignment with "User assignment aborted.  This operation requires all users involved to have a username." and assigns nobody (UISAUTHCOM-103; C1504509).
36. When some Keycloak promotions fail in a batch, the remaining users are still promoted and assigned, and the failures are grouped in one error message (UISAUTHCOM-68; C584420).
37. Unchecking a capability set opens a confirmation stating how many capabilities will be unselected; it can be suppressed for the session, and the suppression resets on re-login (UISAUTHCOM-98; C1395070, C1395071).
38. Unchecking an application that contributes selected items opens a warning with capability and capability-set counts, confirmed with "Continue" (UISAUTHCOM-69, UISAUTHCOM-73; C916226, C926156).
39. Capabilities checked individually before their capability set was checked stay checked after the set is unchecked (UISAUTHCOM-83; C434129, C503019).
40. Column-header "select all" checkboxes affect only the selected applications' capabilities in that action column (UISAUTHCOM-40; C624253, C624254).
41. Capabilities/sets with `visible: false` are hidden in the role form unless "Show hidden capabilities" is checked, and are always hidden in the role details pane (UISAUTHCOM-101).
42. The "Select application" modal marks an application "Assigned" only when the saved role already has a capability from it, and can filter by Assigned/Unassigned (UISAUTHCOM-108).
43. Deleting a role assigned to the current user needs a second confirmation, "Delete currently-assigned role?"; deleting any role removes its user assignments (UISAUTHCOM-102; Confluence).
44. "Share to all" is shown only when the user holds all three share capabilities (role, role-capabilities, role-capability-sets) in Central (UISAUTHCOM-29; C523603).
45. Sharing skips capabilities whose application is not entitled in a member tenant instead of failing, so capability counts may differ per tenant (MODROLESKC-297; C722382).
46. Shared roles and policies cannot be edited or deleted from member-tenant Settings, only through Consortium manager with Central selected (UISAUTHCOM-20, UISAUTHCOM-21).
47. Sharing a Central role whose name already exists in a member tenant is blocked by an inline "Name is already in use at one or more member libraries" error with Save disabled, so member roles are never overwritten (UISAUTHCOM-86).
48. Role names containing the word "and" can be shared (UISAUTHCOM-88).
49. `GET /users-keycloak/_self` returns 401 without an access token, and by default returns all assigned permissions, including hidden ones and those from capability sets (Karate `self.feature`; MODUSERSKC-165, MODUSERSKC-138, MODUSERSKC-52).
50. Login with a wrong password or an unknown username returns 401 with no auth cookies, and the error never reveals which one was wrong (Karate `verify-login.feature`; STCOR-703, MODLOGINKC-72).
51. "Account is disabled…" appears only when an inactive user enters correct credentials, for central- and member-tenant users alike; wrong credentials always give "Invalid username or password." (KEYCLOAK-101, KEYCLOAK-99; C1030031, C1030032).
52. Forgot password/username endpoints always return 204; no email is sent when no user or several users (in ECS: across all tenants, matching email, phone or mobile) share the identifier (MODUSERSKC-111, MODUSERSKC-83, MODUSERSKC-106).
53. Forgot password accepts username, email or phone; Forgot username accepts email or phone; both fields are marked required (STCOR-1020, STCOR-1091; en.json `label.forgot*CallToAction`).
54. Account-activation and reset-password emails contain a working "request a new link" URL to the tenant's forgot-password page (default `/forgot-password`) (MODUSERSKC-180).
55. On the Keycloak login page, Username and Password are marked required (`Username *`, `Password *`); "Or sign in with" appears only when SSO is configured; in ECS dropdown login the "Return to tenant/library selection screen" link survives a failed attempt (KEYCLOAK-130, KEYCLOAK-128, KEYCLOAK-51; C1563889).
56. The login logo's alt text is the realm Display name, falling back to the tenant name (KEYCLOAK-127; C1574516).
57. `POST /authn/logout-all` requires an access token (401 without, 204 with) and works across Central/Member tokens in ECS (MODLOGINKC-74).
58. Logout invalidates only the current session; logout-all invalidates every refresh token of the user (Karate `verify-logout.feature`, `verify-logout-all.feature`).
59. Every logout (manual, idle, FLS) sends `POST /authn/refresh` before `POST /authn/logout`, and no refresh follows the logout page (STCOR-1068, STCOR-1108; C1464078, C1464261, C1464262).
60. The idle-session modal is suppressed when the fixed-length session ends before the modal's countdown (STCOR-884).
61. Without overrides the idle timeout is 4 h with a 1 min modal, and the FLS warning is 1 min (stripes-core `src/components/Root/constants.js`; STCOR-962).
62. New tenant realms get RTR configured, 18 h session limits, a 5 min access token, `unmanagedAttributePolicy = ADMIN_EDIT` and Internationalization on (MGRTENANT-76, MGRTENANT-55, MGRTENANT-95, MGRTENANT-110).
63. When the tenant's entitlements change during a session, the banner "FOLIO has been updated." with "Click here to reload." appears after the next poll (default 15 min) (STCOR-780; en.json `stale.*`).
64. A user whose `expirationDate` has passed is inactive in Keycloak and cannot log in (MODUSERSKC-154).
65. Usernames with uppercase letters log in normally, including migrated ECS users with a member-tenant primary affiliation (KEYCLOAK-87, MODUSERSKC-119).
66. Role CRUD capability sets and role/user assignment capability sets are independent: Manage assignments does not grant role create, and vice versa (UIROLES-125; ui-authorization-roles package.json).
67. Assigned-user names on a role are links only when the viewer can access the Users app (UISAUTHCOM-42).
